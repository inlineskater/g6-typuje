# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Rynek Proroctw G6** — a company prediction market web app with virtual coins, a shared Texas Hold'em table, and small office games. Polish UI. Single static file (`index.html`) backed by a hosted Supabase project and Supabase Edge Functions for server-owned game actions.

Live URL: `https://inlineskater.github.io/rynek-proroctw-g6/`

## Deployment

There is no build step. Push to `main` → GitHub Actions copies `index.html` to GitHub Pages. That's the entire pipeline.

To apply database changes: paste the relevant SQL into the Supabase SQL Editor (Dashboard → SQL Editor → Run). There is no migration runner.

- `supabase/crash.sql` / `supabase/functions/crash-action` — „Rakieta" (Crash) **solo** casino game; each player flies their OWN rocket (`crash_rounds`, one `running` row per user), the hidden crash point/time lives in `crash_round_secrets`, and the Edge Function (`start`/`state`/`cash_out`) owns the RNG, the lazy bust-on-read resolve, and the payout. Results land in `crash_spins` (wired into `economy-stats`/`hazard-views`/`coin-inflow-stats`). No shared table, no realtime; the client animates a freeze-proof per-frame delta-time clock and polls `state` to catch the crash. Postaw runs a **client-side 3 s launch countdown** (`CRASH_COUNTDOWN_MS`, big 3-2-1 digits + canvas ignition/smoke via `drawCrashScene('countdown', …, ignition)`) before `start` is invoked — coins commit only at zero, and a frozen RAF (tab switched mid-countdown) aborts the launch instead of firing it unwatched; `start` then creates the round with `started_at = now() + LAUNCH_HOLD_MS` (1 s in the future), so the client receives the response while the multiplier is still pinned at x1.00 (`elapsedMs` is NEGATIVE during the hold; `crashTick` renders the START! liftoff frame until it crosses zero) — liftoff is synchronized on screen and the rocket never has an unseen head start. **Cash-out fairness contract (WYSIWYG):** the WYPŁAĆ button value is a CONTRACT — `cash_out` pays the claimed `atMultiplier` EVEN ABOVE the hidden crash point (phantom cents the blind display painted before the reveal reached it), bounded by (a) arrival ≤ `CASHOUT_GRACE_MS` (450 ms) after `crash_at` and (b) a cap of `multAt(server elapsed + CLIENT_AHEAD_TOL_MS)` (250 ms legit display lead, mirrored by the `crashShownMs` clamp in `index.html`); a bot claiming the cap every round still loses ≈2% (`(1-HOUSE_EDGE)·exp(CRASH_GROWTH·700) ≈ 0.981`), so `cashout_multiplier` may legitimately exceed `crash_point` in `crash_spins`. Busts are revealed IMMEDIATELY (`resolveDueRound` flips the round the instant `now() ≥ crash_at`) and the grace works even on a round a racing 250 ms state poll just flipped to `busted` — `cash_out` locks the latest running-or-recently-busted round and converts the recorded 0-win spin back into the win (supersedes both the strictly-below-crash-point rule and the earlier delayed-reveal fix). To keep honest clicks inside the grace window, `start` schedules a **bust nudge** via `EdgeRuntime.waitUntil`: the worker sleeps until `crash_at`+120 ms, then POSTs a service-role Realtime broadcast (topic `crash_<roundId>`, event `bust`, empty payload — no secrets) that the client (`crashSubscribeBustNudge`) answers with a `state` pull, landing the explosion in ~150 ms; the 250 ms poll remains the fallback when the worker is evicted (>~150 s flights are capped by `MAX_MULT` anyway). **Parity contract:** `CRASH_GROWTH = Math.log(2)/15000` (doubles every 15 s — slowed from 10 s in 2026-07 so a given latency gap costs less multiplier) must match between `index.html` and the Edge Function
- `supabase/wheel.sql` / `supabase/functions/wheel-action` — displayed to players as **„Koło Żubra G6"** 🦬 (a Żubrówka/bison-grass-vodka reskin of the wheel; every internal identifier stays `wheel` — `wheel_spins`/`wheel_rounds`/`wheel_round_bets`, `wheel-action`, `WHEEL_*` constants, the `'wheel'` game key in stats views/`ACT_GAME_LABELS` — only user-facing strings changed) — a SHARED-ROUNDS casino game: ONE communal wheel with a SINGLE ordered set of 20 segments, no risk tiers (a bet is just a stake): 1× ×10 (jackpot 🦬), 3× ×2, 2× ×1 (ZWROT — stake back), 2× ×0.5 (half stake back), 12× ×0. Sum = 19.0 → **RTP 95.0%**. A round opens `betting` the moment the first player bets; `wheel_rounds` (`id`, `status`, `spin_at`, `segment_index`, `resolved_at`) and `wheel_round_bets` (`round_id`, `user_id`, `nick_snapshot`, `total_bet`, `ready`, `multiplier`, `total_won`, `UNIQUE(round_id,user_id)` — one bet per player per round) are both public-SELECT/no-client-write, realtime-published tables, mirroring the roulette pattern; `wheel_rounds_single_betting_idx` (partial unique index on `status='betting'`) guarantees at most one open round at a time. **Coin timing follows the ROULETTE convention:** `bet` only validates the caller's balance (locks the profile row FOR UPDATE, does not deduct) — coins move for every bet at once when the round resolves. **Resolution is lazy-on-read, crash-style:** `resolveDueRound` (SELECT ... WHERE status='betting' AND spin_at<=now() FOR UPDATE SKIP LOCKED) runs at the top of `state`, `bet`, and `ready`, so the frontend's 1 s poll on `state` (while a round is `betting`, gated by tab-active+visible) is what actually fires a due spin — realtime (`wheel_rounds`/`wheel_round_bets` postgres_changes) only tells clients something changed and triggers the same reload, it never drives the resolve itself. The betting window is `WHEEL_BETTING_WINDOW_MS` = 15 s (duplicated between `index.html` and the Edge Function; the server's `round.spinAt` is always authoritative — the client computes a clock offset from `serverNow` on every response for a synchronized countdown/spin across tabs). After betting, the same button becomes a `ready` vote: the Edge Function marks that bet's `ready` flag under the round lock, and when no unready bets remain it pulls `spin_at` forward to `LEAST(spin_at, now() + WHEEL_READY_GRACE_MS)` with a 3 s sync grace; a solo bettor can therefore fast-start too. **Lock ORDER is round row, then profile row**, identical in `bet()` (find-or-create the open round FOR UPDATE, then lock the caller's profile), `ready()` (round only), and `resolveOneRound()` (the due round is already locked via `resolveDueRound`'s FOR UPDATE before any bettor's profile row is touched) — so the paths cannot deadlock. The Edge Function draws one `segment_index` (0-19) server-side via `crypto.getRandomValues` rejection sampling and pays every bet on the round `floor(total_bet × SEGMENTS[segment_index] × luck)`, mirroring each payout into `wheel_spins` (unchanged shape minus the removed `risk` column — still one row per resolved bet, hazard/economy views need no changes) — a bettor who spent their coins elsewhere before the draw is skipped (`multiplier=0, total_won=0`, no charge, no payout). **Parity contract:** the ordered 20-element multiplier array (`WHEEL_SEGMENTS` in `index.html`, `SEGMENTS` in the Edge Function) must stay byte-for-byte identical — it literally IS the wheel. Gets the „Amulet Bezwstydnego Fartu" ×1.01 casino-luck boost like the other house games (`hasCasinoLuck`, copied verbatim from `plinko-action`), applied once per round draw (same luck roll for every bettor); `state` also returns `casinoLuckUntil` (aggregate `MAX(expires_at)` via `casinoLuckStatus`). Every house-casino tab shows a communal amulet banner with its game-specific effect and exact expiry (or an inactive hint) linked to the shop; the shop card shows the exact projected end date if bought now, stacking the item's duration onto the active shared window. House game: coins move directly on `profiles.coins`, no `coin_transactions` ledger rows. Frontend (`#tab-wheel`): a live "Zakłady tej rundy" panel shows every bet as it's placed (nick/stake/ready, gaining a win/loss result after resolve), a communal "Ostatnie rundy" strip (last 10 resolved, sector + biggest winner), plus the existing personal "Twoje zakręcenia" history from `wheel_spins`; after the bet is accepted, the POSTAW button (`.rl-btn.is-gold`) becomes the ready control. The canvas (`drawWheelBoard`) renders a single big ring (all the visual budget the removed risk tiers freed up — oversized multiplier labels, a decorative dark bezel, a gold bezel ring) painted in a **Żubrówka palette** (0x deep bottle green, 0.5x dried-straw/hay, 1x pale meadow green "ZWROT", 2x vivid bison-grass chartreuse, 10x molten gold with a 🦬 in the label) + a ~40-dot warm-gold LED rim that idle-pulses and CHASES during a spin + a dark-green center hub with a single tapered blade-of-grass bezier (the classic bottle motif) and a 🦬 mark, all driven by one continuous `requestAnimationFrame` loop (`wheelFrame`/`wheelUpdateAnimState`) that walks `idle → countdown → blind → landing → result`: a BLIND constant-velocity spin (`WHEEL_BLIND_SPEED`, ~2.5 rev/s) starts the instant `spin_at` passes locally with no result yet, then blends into an ease-out-cubic landing (`WHEEL_LANDING_DURATION_MS` = 3.5 s, whole-turn math reused from the old solo spin) once `segment_index` arrives; a tab that loads mid-spin with the result already known skips straight to a full reveal-style landing. `plinkoReducedMotion()` skips the blind spin/LED chase and jumps to a 300 ms settle. The nav button and page title carry a small pulsing „NOWOŚĆ" pill (`.wheel-nowosc-badge`, same pulse recipe as `.seasonal-dot`). Stats wired into `hazard-views.sql` (`hazard_stats.wheel_pl`, `game_transactions` UNION — hazardista column header shown as „Żubr"), `coin-inflow-stats.sql`, and `economy-stats.sql` (`hazard_house_net`) — all unchanged, since they only read `wheel_spins`. ## Architecture

Everything lives in `index.html`: HTML structure, all CSS (CSS variables for theming), and all JavaScript in one `<script>` block. No bundler, no framework, no TypeScript.

**Supabase client** is loaded from CDN. The anon key is intentionally public — Supabase RLS and function grants are the security boundary.

### Key global state

| Variable | Contents |
|---|---|
| `me` | Logged-in user profile (`id`, `nick`, `coins`) |
| `markets[]` | All market rows from DB |
| `tradesByMarket{}` | All individual trade rows, keyed by `market_id` |
| `myPositionsByMarket{}` | Current user's aggregated positions (from `positions` view) |
| `pokerState` | Sanitized shared poker table state returned by the Edge Function |
| `whackBossRuntime` | Current local Whack-a-Boss round timing, clicks, and score |

### Data flow

1. `loadMarkets()` fetches markets, trades, and profiles in parallel then calls `renderMarkets()`.
2. `renderMarkets()` fetches the current user's positions (`positions` view), then calls `buildMarketCard()` for each market.
3. Realtime subscriptions on `markets` and `trades` tables update state and call targeted update helpers (`updateCardProb`, `updateCardChart`) instead of full re-renders where possible.

### Auth

Nick + 5-digit PIN. Implemented as Supabase email/password auth using the synthetic email `nick@typuje.local`. A Postgres trigger (`handle_new_user`) creates the `profiles` row on first signup. Economy writes go through RPCs or Edge Functions; the admin-only garden stage/streak controls use column-limited direct updates protected by RLS.

### CPMM pricing

`p(YES) = no_shares / (yes_shares + no_shares)`. Markets start at `yes_shares = no_shares = 500` (50%). Constant product `k = yes_shares × no_shares` is maintained by `place_bet`. Shares out for a NO bet of X coins:

```
dN = (N × X) / (Y + X)
sharesOut = X + dN
```

### Payout formula

Resolution distributes the total pot via the RPC `resolve_market`. The formula (mirrored in `estimatePayout()` for the live UI estimate):

```
payout = user_amount_bet + losing_side_pot × (user_shares / total_winning_shares)
```

Winners always get at least their bet back; the losing side's coins are split proportionally by share count. The estimate and the actual SQL resolution use identical math.

### DOM helper

`el(tag, attrs, ...children)` creates DOM nodes. **Children must be strings or Node objects — never arrays.** When you need to mix text and multiple element nodes outside of `el()`, use `node.append(str, node, str, ...)` instead.

### Permissions

All mutations require authentication and go through Supabase RPCs:
- `place_bet(market_uuid, side, amount)` — enforces coin balance, side-locking (can't bet both sides on the same market), and CPMM math atomically
- `create_market(icon, title, deadline)`
- `resolve_market(market_uuid, resolution)` — only market creator or a profile with `is_admin = true` can call this

Users can only add to one side per market (side-locked after first bet). Profiles with `is_admin = true` can resolve any market.

### Marketplace (Targowisko)

The Sklep tab contains a peer-to-peer marketplace ("Targowisko 🛍️") where **any logged-in user** can list IRL goods or services for coins. Unlike the admin-only store rewards and hero-item auctions (where coins are burned), marketplace coins **transfer from buyer to seller**. Two listing formats are supported: fixed-price (`listing_type='fixed'`, instant buy) and timed auction (`listing_type='auction'`, bidding with escrow). The bidding engine mirrors `place_hero_item_bid`: coins are escrowed on each bid, the previous leader is auto-refunded when outbid, and the leading bidder only pays the incremental difference to top up their own bid. Settlement (`settle_marketplace_listing`) credits the escrowed winning amount to `seller_id`. Sellers (or admin) can settle their own auction; sellers can cancel an open listing with no bids. All RPCs are in `supabase/marketplace.sql`; the `marketplace_cards` view is used for card rendering.

### Poker

Poker is one shared authenticated Texas Hold'em table. Browser clients call `sb.functions.invoke('poker-action', ...)`; they do not write poker tables directly. The Edge Function verifies the user JWT, uses `SUPABASE_DB_URL` for a Postgres transaction, and stores hidden cards/deck in service-only tables. Public realtime updates on `poker_tables`, `poker_seats`, and `poker_events` only trigger a sanitized state reload.

Table defaults are 100 coin buy-in, 1/2 blinds, 6 seats, and a 30 second action timer. Sitting deducts the buy-in from `profiles.coins`; standing is allowed only between hands and returns the remaining stack. The leaderboard view includes active poker stacks so seated players keep their net worth while playing.

### Roulette (Ruletka)

Roulette is one shared authenticated table (`supabase/roulette.sql` + the `roulette-action` Edge Function; `verify_jwt` off, JWT checked per action). Up to 6 players sit in `roulette_seats`; coins are deducted **only at spin/resolve time** (`resolveRound`), never at bet time — so dropping a seat's open bets refunds nothing. The frontend (`#tab-roulette` → `loadRouletteState`/`renderRoulette*`) is a CSS-grid rounded-rect felt: a control dock on top, wheel + number board side-by-side, an on-felt seat strip, and a lower band holding the bets list + recent results. The unified button system is `.rl-btn` (`is-primary`/`is-ghost`/`is-gold`); the round chip selector reuses the shared `.casino-chip` (do not edit that base for roulette-only tweaks — scope under `.roulette-chips`).

**Idle-seat auto-eviction:** abandoned (closed-tab) seats are freed poker-style — `getState` runs `evictStaleSeats` on every read, deleting any seat whose `last_seen` is older than `SEAT_STALE_MS` (90s, server-only constant in `roulette-action`) and bumping the caller's own `last_seen`. The browser pings `state` every `ROULETTE_HEARTBEAT_MS` (25s, in `index.html`) while on the tab + visible + seated, plus on `visibilitychange`. The two constants are coupled: keep the client heartbeat ≤ ⅓ of the server threshold. `last_seen` lives on `roulette_seats` (idempotent `ADD COLUMN IF NOT EXISTS`).

### Plinko G6

Plinko G6 is a solo authenticated house game (`supabase/plinko.sql` + `plinko-action`). The browser calls the Edge Function directly with the active Supabase access token for `state`, `drop`, and queued `drop_batch` requests; it never writes tables directly and never chooses the path. The Edge Function validates stake/rows/risk, locks `profiles.coins`, generates crypto-random left/right paths, writes `plinko_spins`, updates the balance, and returns completed drops. The frontend (`#tab-plinko`) is an Office Arcade canvas board: glowing pegs, G6 ball trail, bucket bursts, paper/calculator/coffee particles, reduced-motion fallbacks, top-positioned start button, timed requests, and rapid-click queue playback. The payout tables live in both `index.html` (`PLINKO_PAYOUTS`) and `plinko-action`; keep them in sync, and re-run `hazard-views.sql`, `coin-inflow-stats.sql`, and `economy-stats.sql` after installing.

### Miny G6

Miny G6 is a single-player authenticated casino game (`supabase/mines.sql` + `mines-action`). The browser calls `sb.functions.invoke('mines-action', ...)` for `state`, `start`, `reveal`, and `cash_out`; it never writes tables directly and never receives mine positions while a round is active. ### „Uzdrowiciel G6" (`healer_dungeon`) — full seasonal game since 2026-08

A WoW Classic **dungeon healer**, added 2026-07-27, promoted from arcade-only to a full seasonal game 2026-08 (debut via override on the week starting 2026-08-03 — see the Seasonal games section above). **Five-man party** (`HD_PARTY` = 5 — tank / you / three dps), an **endless** dungeon where every pull is harder, **every fifth pull is a boss**, and the run ends the moment **anyone hits 0 HP**. **Score is POINTS** (2026-07-29 — see the scoring section below), not pulls cleared, and the run ends only when **YOU** die. Lives in `games/healer-dungeon.js`; the panel is `#seasonal-game-healer-dungeon`, parked with the seasonal panels inside `#tab-whack-boss`'s `<main>`.

**Phase 1 (2026-07-27 → 2026-08) was deliberately arcade-only** while the sim's damage/mana curve was still being tuned — "tune first, then transcribe," since once a parity contract exists every balance tweak means editing two byte-identical copies and re-running a fuzzer. **Phase 2 is now live**: `supabase/healer-dungeon.sql` (tables/views/`award_healer_dungeon_week()`/cron, same shape as every other seasonal game — see the file listing near the top of this document) and `supabase/functions/healer-dungeon-action` (a byte-for-byte Deno transcription of the fenced `╔═══ PARITY BLOCK START` / `╚═══ PARITY BLOCK END` region of `games/healer-dungeon.js`, verified by `scripts/hd-parity.mjs`) now own the real seed, the real replay, and the real weekly payout. Two things about this game's seasonal integration don't have a precedent in any earlier seasonal game:
- **The class is chosen before the round starts, and it changes the numbers the sim computes** (every `HD_CLASSES`-indexed spell table differs by class) — so unlike every other seasonal game, where only the seed is server-issued, `start` also takes a client-declared `cls` (0-3) and stores it on the round row, threaded through `hdReplay` exactly like the seed. There's no cheat vector in letting the client pick its own class: all four are balance-asserted to the same HP-per-mana by `hd-balance.mjs`, so nothing is gained by lying about which one was played — the leaderboard just prints the wrong class icon if a client ever sent a mismatched one, which the `[0,3]` range check on `start` already prevents.
- **A round has no natural "clean" end.** Every other seasonal game's replay distinguishes `died` from `completed` (a top-out, a full board, a survived timer); a healer dungeon run only ever stops on the healer's death or the `HD_MAX_TICKS` (12000 = 20 min) replay-cost safety cap — there is no third outcome, so `hdReplay`'s `completed` flag is really just "hit the safety cap without dying," and `submitRound` accepts either.

**Dual-mode like Tetris**: played from „Wszystkie Gry" it still starts a REAL server round (`invokeHealerDungeon({action:'start', cls})`) so the seed is never guessable and the round row exists for auditing, but `archiveMode` (set from `allGamesMode` at start time) routes the finish through `recordArcadeScore('healer_dungeon', score, {cls,icon,name})` instead of a trusted `submit` — the arcade leaderboard still shows the class via `client_meta`, the seasonal leaderboard via its own typed `cls` column. **No hero-item `score_bonus` integration** (deliberately, documented inline in `submitRound`): the other seasonal games' flat "+N points" bonus doesn't map cleanly onto a four-component weighted score (depth/healing/flawless/tempo) the way it does onto a raw pull/line/kill count.

**The seasonal leaderboard UI lives inside the startcard, collapsed by default** (`#hd-board-toggle` / `#hd-board`, `renderHealerDungeonState`/`renderHealerDungeonTable`/`renderHealerDungeonAwards` in `games/healer-dungeon.js`) rather than as a side panel like every other seasonal game's `.bj-board-panel` — the console is a fixed-size, never-scrolling viewport takeover (see below), so a permanently-visible sidebar would either shrink the game board or risk overflowing the fixed virtual canvas. The panel scrolls internally (`max-height` + `overflow-y`) instead. `healerRuntime` itself is **pre-declared in `index.html`** (`let healerRuntime = null;`, alongside every other lazy-loaded game runtime like `tetrisRuntime`) rather than in `games/healer-dungeon.js` — this file only assigns it — because `loadSeasonalTab()` needs to reference `healerRuntime`/`healerEnterView`/`healerExitView` before the lazy-loaded script has ever run, and a second top-level `let` for the same name across classic scripts sharing one global scope is a `SyntaxError`.

**Controls — MOUSEOVER CASTING + CLICK-CASTING** (2026-07-29 rev 4, replacing target-then-cast). ⚠️ **The target STEP was the problem, not the keybinds.** Every heal used to be two inputs — pick a target with 1-5, press a spell on Q/W/E — inside a 1.1 s global cooldown, which is why it played like queuing orders instead of reacting. Almost nobody who heals seriously in an MMO uses target-then-cast; they use one of two schemes that collapse it to ONE input, and both are live here at once because they do not conflict:
- **Mouseover**: hover a raid frame *or* a hero on the battlefield and press **1 / 2 / 3**. The spell goes to whoever is under the cursor — there is no target to set. (Q/W/E stay as aliases for anyone who learned the first build.)
- **Click-cast**: left / right / middle-click a frame casts spell 1 / 2 / 3 on it directly, for playing with the mouse alone. **Shift+left aliases middle**, which is unusable on a trackpad, and both `contextmenu` and `auxclick` are suppressed on frames and canvas.

The keys map to SLOTS, not to named spells, so they mean the same three things in every class. **There are no target keys any more** (`HD_TARGET_KEYS` is gone, and so is the digit badge on each frame). What remains is a **sticky target**: `healerSetHover` records the last unit you hovered or clicked, and `healerCastTarget()` falls back to it when the cursor is in dead space — without that, a keypress with the mouse parked anywhere else would silently do nothing, which reads as a broken game rather than as a missing target. The frame under the cursor is outlined in loud blue (`.is-hover`) and the sticky target in quiet amber (`.is-target`); the battlefield paints the same two states on the hex. ⚠️ **Touch keeps the old two-step model** — `hdIsTouch()` routes a tap to `healerSetTarget` and the on-screen spell buttons do the casting, because hover does not exist and there is no second mouse button. ⚠️ **`healerCanCastNow()` blocks casting outside a fight**: the frames stay on screen and clickable during a rest, and with click-casting a stray click while reaching for an upgrade card would silently drain mana you never get back (the refill happens once, when the rest begins). It is guarded in the three cast entry points rather than in `hdCast`, so the rules the balance harness measures are untouched. `hdCanvasPoint()` still has to undo two transforms to map a click back: the console's CSS scale (which `getBoundingClientRect` already folds in) and the canvas's `object-fit: contain` letterboxing (which it does not — the element box is not the drawn box).

**All the pressure is INSIDE one pull** (2026-07-28 rework). There is no dungeon timer, no rest timer and no drinking: a pull runs until the pack is dead, then the party sits as long as it likes, health and mana return to FULL, the player takes a bonus and pulls when ready (`HD_A_PULL` is refused until `upgradePicked`). Removing drinking while making the rest unlimited left no third option — out-of-combat regen would refill the bar anyway, so making the player watch it tick up is tedium, not a decision. ⚠️ This deliberately replaces the old between-pull attrition economy: the game is now a per-pull skill check, and difficulty must be tuned INSIDE the fight. A pull runs ~21 s and spamming the filler costs ~80 mana/s, so a full 1500-mana bar is roughly one fight — you get deeper only by healing more efficiently. The **5-second rule** (`HD_FSR_TICKS` = 50) still governs regen, so the gaps you leave mid-fight are where the next fight's mana comes from, and **spell efficiency** (filler ~2.4 HP/mana · raid spell ~2.7 across all five · panic button ~1.75) is the whole skill test. The filler **replaces itself** on a target, so one HoT/shield caps single-target sustain.

Damage arrives on **four** independent beats so the five bars never fall evenly: tank melee every 1.8 s, a party-wide AoE every 8 s **with the jitter rolled per target** (one shared roll left all five in lockstep, so the party read as a single health pool), a heavy spike on a random non-tank every 10.5 s, and a **cleave on two different heroes** every 7 s.

⚠️ **Tuning this is not guesswork — use a sweep.** With full restore, the balance is a narrow ridge and the two obvious knobs fight each other: raise the boss and every run dies at pull 5; lower it and normal pulls never kill anyone, so every score in the field is 4, 9 or 14. A parameter sweep over the per-pull damage ramp × melee base × boss HP found that **no configuration keeps both a fat boss and the 7-11 target band**, which is why `HD_BOSS_HP_MULT_PCT` is only **110** — a boss is a MECHANICS step (telegraphed casts + enrage), not an HP sponge, and `HD_BOSS_MELEE_PCT` is back to 100 because a multiplier on a long fight is paid many times over. Current point (rev 2, after deaths stopped ending the run): melee 86 +21/pull, AoE +19, spike +40, cleave +24, pool 1500, boss HP ×1.00 → avg **9.4 pulls** across the three classes at ~3.5× a no-heal run, ending on **seven distinct depths (6-14)** with only half of them on a boss. ⚠️ **All stale as of 2026-07-30**: `HD_BOSS_HP_MULT_PCT` is now **100** (see the note further down on why even a 10% bonus became the wall 88% of runs died on once deaths stopped ending the run), `HD_BASE_MANA` is **2900** and the DPS ramp is slower (fights ~32 s, not ~21 s) — see "Fights are SLOWER" below — and there are **four** classes, not three. The method (sweep, read the properties out of the sim, do not hand-restate them) is what is still current; the specific numbers in this paragraph are a snapshot of the pre-4-class tuning pass. ⚠️ The sweep that found this only moved ONE knob that mattered — boss HP. Boss ability damage and the normal-pull spike were swept over ±30% and changed the field by less than half a pull; if the field ever buckets again, look at fight LENGTH before you look at damage. ⚠️ The GCD is a *difficulty* knob disguised as a feel knob: dropping it 1.5 s → 1.1 s raised the spam rate from 60 to ~82 mana/s against unchanged regen, which is why `HD_BASE_MANA` went 1200 → 1500 in the same pass.

**FOUR HEALING CLASSES, picked before the run** (2026-07-29, Szaman added 2026-07-30): `HD_CLASSES` holds `druid` / `priest` / `paladin` / `shaman`, each with the same three ROLES in the same three slots — slot 0 the efficient filler, slot 1 the raid-wide answer on a cooldown, slot 2 the expensive panic button — so every readout, keybind and bot policy is class-generic and `st.cls` is the only thing that changes. **„Same power" is a hard constraint enforced numerically, not by feel**: `hd-balance.mjs` asserts that each slot's HP-per-mana agrees across ALL classes to within **3%** (filler ~2.4 · raid ~2.7 · panic ~1.75). What differs is *when* the healing lands, which is the entire identity of a healing class — Druid HoTs (nothing wasted, everything late), Kapłan **absorb shields on the filler** (stop the hit instead of repairing it; perfect against a telegraphed cast, pure waste otherwise), Paladyn direct heals (instant and exact, and the only panic button with no cast time, paid for with a 15 s cooldown), **Szaman a HoT filler + instant raid heal + an absorb shield on the PANIC button instead of the filler** — the first class whose emergency tool is preventive rather than reactive: it has to be pre-cast, it cannot answer a hit that already landed. Shields are a real mechanic, not a reskin: `st.shield[]`/`st.shieldT[]`, consumed first inside `hdDamage`, absorbed damage counted as **effective healing**, and a shield that expires untouched counted as **overheal** — which is what keeps the score's precision term honest across classes. ⚠️ **A HoT's tick RATE is a balance knob independent of its totals, in TWO different ways.** The druid's original bug was arrival latency: at one tick every 3 s the HoT delivered identical HP-per-mana but arrived so late that spike damage killed the target first, fixed by ticking every 2 s (`period: 20`, Dziki Wzrost 15) without touching the total. The shaman's launch bug was different: a *shorter total duration* at equal total value and cost passed the per-cast "same power" check perfectly (HP-per-mana is a snapshot, not a rate) but meant a blanket-style policy keeping 5 targets covered had to recast far more often, which is a MAINTENANCE-RATE cost (`5 × cost ÷ duration` mana/s) the per-cast check cannot see — 56 mana/s for Odnowa's 8 s HoT vs 75 mana/s for a 6 s one at the same value. Przypływ now ticks in 6 smaller pieces over the SAME 8-ish seconds (`period: 13`, six ticks), so it still feels faster without quietly costing more to maintain. ⚠️ **The shaman still measures weakest of the four in the harness bot** (see the `hd-balance.mjs` note by the class-balance check) — its panic button asks the bot to predict, and the bot's maintenance-loop policy is a cruder approximation of that than the reactive-heal logic the other three get; the ≤3% per-spell spread is the real fairness guarantee, the bot average is not. The choice is remembered in `localStorage` (`hd_class_v1`) and re-seats the idle sim immediately so the frames, spellbook and character pane preview the class before you start. **Paladyn is the default for anyone who has never chosen** (`HD_CLASS_DEFAULT`) — no HoT/shield timing to learn, so a first heal behaves like clicking a heal in any other game; distinguishing "never chosen" from "explicitly chose Druid" needed reading the raw `localStorage` string, since `Number(null) || 0` and `Number('0') || 0` are both `0`.

**Casts are FAST** (2026-07-29): `HD_GCD_TICKS` is **11** (1.1 s, was 15) and every cast time came down with it — druid's panic button 1.6 s, priest's 2.0 s, paladin's is instant on a cooldown, paladin's filler is a 1.4 s cast. A healer's inputs should feel like reflexes, not like queuing orders. See the tuning note above for why this is also a difficulty change.

**Score is POINTS, banked pull by pull** (2026-07-29, replacing „pulls cleared" — which made every leaderboard a three-bucket affair and said nothing about *how* you cleared them). `hdBankPull` runs the instant a pack dies, so `st.score` is always the score you would submit if you died right now, and it splits into four terms shown **only on the result card**:
- **🏅 Głębokość** — `(1 + floor((pull−1) / HD_SCORE_DEPTH_EVERY 2)) × (boss ? HD_SCORE_BOSS_MULT 2 : 1)`. The dominant term; depth is still what the game is about.
- **💚 Leczenie** — `floor(effective / HD_SCORE_HEAL_PER_PT 3000)` **then scaled by PRECISION** (`effective / (effective + overheal)`), so a wasted heal costs exactly its own share of the points. Absorbed damage is effective; an expired shield is overheal.
- **🔥 Bezbłędność** (2026-07-30) — flat `HD_SCORE_FLAWLESS_PTS` (1) for a pull with `st.pullDeaths === 0`, else 0. A death already costs dps and stretches the fight (`hdPartyDpsPerTick`/`hdLivingDps`), but that was an INDIRECT cost — a run that shrugged off a death because it still cleared the pull paid nothing extra in the one number everyone compares. `st.deathPulls` (pulls with ≥1 death) also drives the result card's "N/M grup bez straty" line.
- **⏱️ Tempo** — `HD_SCORE_TEMPO_MAX 2 − 1 per HD_SCORE_TEMPO_SEC 5 s of the preceding rest`, locked in at `hdStartPull`. This is how time pressure comes back **as score rather than as a mechanic**: the rest stays free and unlimited (which is right — see the paragraph above), but confidence pays. Nobody is ever forced to pull early. ⚠️ The OPENING pull always banks full tempo (there was no rest before it), so a permanently dawdling run bottoms out at 2, not 0.
**The numbers are deliberately DOZENS** (rev 2): a good run measures **30-60** and the deepest plausible one stays well under the 999 arcade cap. Four-digit scores read like a pinball machine and made a one-pull difference invisible; two digits are a number you can hold in your head. **There is no live score readout** — `#hd-scorecard` and the score/pull/mana top-bar chips were all removed. In a fight you are meant to be looking at five health bars, not a counter. **The class you played rides along with the score** (2026-07-30): the result card leads with a `🏅`-style class header (`hdClass(st)`), and `finishHealerDungeonRound` passes `{cls, icon, name}` as a third `p_meta` argument to `recordArcadeScore` — a small `client_meta jsonb` column on `arcade_scores` (generic across every arcade game, not healer-specific) that the picker and per-game leaderboards print as an icon prefix on each row when present. `record_arcade_score`'s old 2-arg signature was DROPped rather than left alongside a 3-arg default-NULL overload, because Postgres resolves an exact-arity call over one needing a default — keeping both would have left the new one dead for every existing 2-arg caller.

**THE RUN ENDS ONLY WHEN THE HEALER DIES** (2026-07-29 rev 2). A fallen ally used to be an instant game-over, which meant one unlucky spike erased a whole run and the only lesson available was "that was unlucky". Now a corpse stays down for the rest of the pull and **takes its damage with it**: `hdPartyDpsPerTick` scales by `hdLivingDps`, so the fight gets longer while the incoming damage does not — a death spiral you can still try to heal your way out of. `hdBeginRest`'s full restore is also what picks everyone back up, so a death costs the pull, never the run. **With the tank down** the pack turns on whoever is left at `HD_NO_TANK_MELEE_PCT` (135%), because nobody else is built to eat it. Every random target now picks out of the LIVING (`hdPickLiving`, `hdMeleeTarget`) so a corpse never soaks a hit meant to pressure the party, and single-target spells refuse to fire on one rather than eating the GCD. ⚠️ This makes the game **much** easier at the same constants — it is what forced the boss retune below.

**Fights are SLOWER, and mana went up to match (2026-07-30)**: `HD_DPS_BASE`/`HD_DPS_PER_PULL` went 90/22 → 58/15, stretching a pull from ~21 s to ~32 s. The reason isn't pacing for its own sake — a ~21 s fight fit into 5-8 casts, which meant the 5-second rule almost never had to be USED, only known about: the fight was over before you needed a second deliberate gap. A longer fight makes "cast on every GCD, no exceptions" run the mana pool dry partway through, while banking a few seconds of regen whenever nobody is in danger is what actually finishes it — real, repeated pacing decisions instead of one. ⚠️ Stretching fight length WITHOUT raising the mana budget just makes the game harder in the boring sense (periodic damage sources are unchanged per real second, so a 52% longer fight deals 52% more total damage) — `HD_BASE_MANA` went 1500 → 2900 to compensate, found by sweeping the value until all four classes simultaneously cleared the 7-11 pull band and stayed inside the harness's 40% cross-class spread tolerance (`hd-balance.mjs`'s "no class more than 40% ahead" check). Below that value the shaman (whose predictive panic button trails the other three under the bot's cruder policy for it) dragged the four-class average under 7; above it, mana pressure on the other three thinned out further than it needed to.

**Randomness beyond the talent pool** (2026-07-29 rev 2), because „every pull is harder than the last" is a curve, not variety:
- **Pull affixes** (`HD_AFFIXES`, 9 including „none") roll once per pull and re-weight the same four damage beats — 😤 Wściekła, 👥 Liczna, 💨 Szybka, 🩸 Wysysająca (takes mana), 💥 Wybuchowa, 🗡️ Brutalna, 🍂 Wątła, 🎯 Skupiona. Fields are percentages read through `hdAff()` so a missing field means "unchanged" and a new affix needs no call-site edit. Shown next to the pack's health bar. **Never on pull 1** (the opening must be learnable) and ⚠️ **never on a BOSS** — a boss already draws its own kit, and stacking an affix double-dipped: almost every measured pull-5 death was „Brutalna" (+42% melee) on a boss whose fight is already twice as long, which bucketed the whole field at 4 and 9. **STACKING (2026-07-30)**: from `HD_AFFIX2_MIN_PULL` (8) on, a second, distinct, non-„none" affix can pile onto the first at `HD_AFFIX2_CHANCE_PCT` (30%) — `st.affixes` is an array (0-2 entries) rather than a single index, `hdAffixList(st)` reads it, and `hdAff(st, key)` **compounds** every active affix's value on that key multiplicatively (`pct = floor(pct * v / 100)` per affix) rather than the last one winning; `hdAffixDrain(st)` sums the mana-drain field instead, since that one is an absolute amount, not a percentage. Never stacked on top of „none" (nothing to stack onto). The header line and the in-game help both render every active affix, not just the first.
- **Boss kits**: each boss draws `HD_BOSS_KIT_SIZE` (2 — **3 from `HD_BOSS_KIT_DEEP_PULL` (20)**, 2026-07-30) of `HD_BOSS_ABILITIES` (4) at pull start, so the same named boss plays differently every time — and less predictably once you have already seen every kit a few times. `HD_CB_BUSTER` (one target, huge), `HD_CB_NUKE` (whole party), `HD_CB_FOCUS` („Ocena Roczna", a devastating hit on one of the back line), `HD_CB_DRAIN` („Cięcie Budżetu", `HD_BOSS_DRAIN_MANA` off your bar plus party damage). **The target is chosen when the cast STARTS** and stored on `st.bossCast.tgt`, so the raid frame and the red floor marker can show *who* for the whole 3.5 s — a telegraph you cannot aim at is just a delay. `hdBossAbilityRaw` is the single source for an ability's size, so nothing can reach the cast bar without also being predictable.
- **Office nemesis / boss flavor naming is now SEED-derived, not sequential** (2026-07-30): `hdFlavorHash(seed, pull)` is a small pure integer hash (no RNG-stream consumption) combining the run's immutable `st.seed` (set once in `hdInitState`, distinct from the mutating `st.rngState`) with the pull number, and `hdPackName`/`hdPackGlyph` now take `st` to read it. It used to just cycle `HD_PACK_NAMES` in pull order — same office nemesis on pull 1 of every run — which reads as scripted once you have played a few sessions. Being a pure function of `(seed, pull)` rather than a live RNG draw is deliberate: the rest overlay previews pull+1's name/glyph *before* that pull has started, and a function that consumed the shared PRNG would make the preview lie the moment the real `hdStartPull` rolled something different for real gameplay state.
- **The upgrade hand's shape is rolled**: usually 2 stats + 1 talent, `HD_TWO_PERK_PCT` (35%) of the time 1 stat + 2 talents. There is always at least one of each and never a duplicate.

**Twelve talents, not eight**: the four added in rev 2 are `HD_PK_FSR` (Medytacja — shortens the 5-second rule), `HD_PK_RAID` (Moc Grupowa — the raid spell only), `HD_PK_HASTE` (Szybkie Ręce), and `HD_PK_REVIVE` (Wskrzeszenie — a fallen ally stands back up at `HD_REVIVE_PCT` after `HD_REVIVE_TICKS`, once per pull; only meaningful *because* deaths no longer end the run). ⚠️ **`hdCastTicks` applies Szybkie Ręce to EVERY cast, not just the panic button** — scoped to the panic button it was a dead card for the paladin, whose panic button is already instant, and a talent that does nothing for the class you picked is the worst possible outcome of a random draw. The harness asserts it lands for all three.

**The third upgrade card is a RANDOM talent** (2026-07-29). Every rest deals `HD_STAT_CHOICES` (2) of the three stats **plus one perk drawn from `HD_PERK_COUNT` (12)** — the stat line always advances and the wildcard is always on the table, which a pure random pool could not promise. Perks stack (`st.perks[]`) and each changes something you feel at the keyboard: `HD_PK_REGEN` (+10 mana/s), `HD_PK_GCD` (−0.1 s GCD, floor `HD_GCD_MIN` 7), `HD_PK_CHEAP` (−7% costs, floor 60%), `HD_PK_PHOENIX` (Serce Feniksa — one cheat-death per **pull**, refreshed in `hdStartPull`, the only thing in the game that undoes a mistake), `HD_PK_CDR` (raid cooldown −1.5 s), `HD_PK_WARD` (−6% damage taken), `HD_PK_CRIT` (+10% chance a heal crits for +65%), `HD_PK_FURY` (+25 party dps at +8% damage taken — the one with a downside). ⚠️ **`hdHealRoll` is the only function allowed to consume RNG for a heal, and only when the crit perk is held** — `hdHealAmt` stays pure because `hdIncomingHeal` calls it every frame from the raid frames, and a player without the perk must see a bit-identical run to the one they would have seen before the perk existed. `hdPerkDelta` prints a card's before → after by momentarily bumping the stat and re-reading `hdPerkNow`, so a card can never disagree with the sim.

**An eight-card first-run tutorial** (`HD_TUTORIAL`, `#hd-tut`) fires once on the first ever visit (`localStorage` `hd_tutorial_v1`) and is replayable from the „▶ Samouczek" button in the `?` overlay. A healing sim has more moving parts than anything else in the arcade — five bars, a prediction overlay, a mana rule and a three-term score — and the previous answer was a wall of text behind a button nobody pressed. While it is up it **owns the keyboard** (Enter/→/space advance, Esc closes) so nothing leaks to the game underneath.

**Three upgrade stats, not five** (2026-07-28): `HD_UP_HEAL` (Moc leczenia — raises every heal AND widens the mana pool, so it is the only stat that improves HP-per-mana), `HD_UP_HP` (Życie — max HP for the **whole party**, since with a cleave and a per-target AoE the back four die as often as the tank; the old Wytrzymałość was tank-only), and `HD_UP_DMG` (Obrażenia). Duch and Pośpiech are gone — they changed a background number rather than anything you do — so regen and cast speed are now fixed constants. ⚠️ Rebalance when touching these: three strong stats snowball much harder than five mixed ones, and party-wide HP is far stronger than tank-only. The first 3-stat pass sent a good run from 8 pulls to **14.6**; `HD_UP_STEP` dropping 3 → 2 is what brought it back to 8.5.

**Bosses every `HD_BOSS_EVERY` (5) pulls** are the one encounter that *telegraphs*: every `HD_BOSS_CAST_PERIOD` the boss spends `HD_BOSS_CAST_TICKS` (3.5 s — three GCDs) on one of its two drawn abilities with a visible cast bar. Past `HD_BOSS_ENRAGE_TICKS` (28 s) `hdEnragePct` adds +5 percentage points of damage per second, so a party that never picked Obrażenia cannot out-heal its own slow kill. The scary part of a boss is the cast you can answer, not the autoattack you cannot — which is why it gets no melee bonus at all, and (rev 2) ⚠️ **`HD_BOSS_HP_MULT_PCT` is 100 — no HP bonus whatsoever**. Once a death stopped ending the run, a longer fight was no longer just "more damage to heal": it was more chances for a dps to fall, and every one that fell stretched the fight further. Even a 10% bonus made the boss the wall **88% of measured runs died on**, leaving four distinct scores in the whole field. At 100% it ends half of them, spread across seven depths. `HD_BOSS_AOE_PCT` came down 120 → 110 in the same pass.

**Heal prediction** is `hdIncomingHeal(st, slot)` (every remaining HoT tick plus the in-flight cast) and its mirror `hdIncomingDamage(st, slot)` (the boss ability currently on the cast bar, pre-jitter). The raid frame paints the first as a pale striped block **on** the missing health and the second as a hatched block eaten out of the **right edge** of current health, so "does this bar survive the cast?" is one glance. `hdSurvives(st, slot)` owns that answer for every caller (frame, nameplate, bot) and adds the absorb shield to the same side. ⚠️ Survivability is `hp + incoming + shield > dmg` — incoming healing is on the *same side* as current health. Written the other way round first (`dmg + incoming >= hp`), which made a well-covered target read as *more* likely to die the more healing you had landed on it.

**`scripts/hd-balance.mjs` is the balance harness** — it loads only the parity block out of the game file (the rest touches `document`) and asserts the properties that make the game work, not just that it runs: the 5-second rule is exactly 5.0 s, the HP-per-mana ordering holds, **every slot is within 3% across all four classes**, the raid spell lands on all five in every class, shields absorb / expire into overheal / count toward surviving a telegraph, prediction matches what the HoT actually delivers, bosses telegraph with ≥2 GCDs of warning, enrage ramps, every rest deals exactly two distinct stats + one talent, Serce Feniksa saves and is then spent, **overheal eats healing points in exact proportion**, dawdling costs tempo, runs are deterministic per seed *and per class*, **mana is genuinely the binding constraint**, and **a good run lands in the agreed 7-11 pull band** (currently avg 7.3, ~14.6× a no-heal run, at `HD_BASE_MANA` 2900). Its bot is written entirely against SLOTS so one policy plays every class; ⚠️ the one class-aware branch on the FILLER slot is that a HoT/shield filler must be **blanketed** pre-emptively while a direct one must not — without that branch the bot played druid and priest like a paladin and both measured weak, which is a POLICY artefact that looks exactly like a balance problem. The PANIC slot got its own class-aware branch for the same reason (2026-07-30): a shield-kind panic button (`panicIsShield`) must not be reactively dumped on someone already hurt (a shield does nothing for HP already lost, only the next hit) and instead gets maintenance-looped onto the tank whenever mana is above 30% of max — ungated, that loop consumed nearly every GCD in the run and never let the bot rest at all, which is exactly the "never leaves a gap" failure mode the whole fight-length change exists to punish, just committed by the bot instead of a player. ⚠️ **The class-balance check's 40% tolerance is now genuinely tested**, not just theoretical headroom — the shaman sits at the bottom of it because its panic button asks the bot to predict rather than react, which this policy approximates worse than it approximates the other three; see the comment at that check for why the ≤3% per-spell spread, not the bot average, is the real fairness guarantee. Two scoring checks are deliberately mechanical rather than bot-driven for the same reason: a careless bot that sprays heals dies immediately, so comparing it to a careful one measures survival, not waste — `hdBankPull` is called directly on two otherwise identical pulls instead. Rev 2 added **a per-spell audit (nine spells, now twelve with the shaman)** (every slot of every class: it costs what the button says, takes the GCD, sets its own cooldown, sits on the cast bar for its full cast time and delivers nothing before it ends, lands on exactly its declared targets, ticks exactly `amounts.length` times, refuses a corpse without eating the GCD, and refuses when the mana is not there), **death-rule checks** (an ally can fall without ending the run, a corpse stops contributing damage, the healer dying does end it, the rest picks the fallen up, the melee finds a new target with the tank down, Wskrzeszenie stands someone back up), **affix and boss-kit checks** (pull 1 and bosses are never modified, every affix is reachable and actually moves HP or the timers, all four boss abilities appear and every one is predictable on the right victims), and **the three-bucket test** — deaths must land on ≥6 distinct depths with ≤70% on a boss, which is the check that caught the boss HP bonus. ⚠️ A per-spell test must snapshot health **before** the casting tick: an instant resolves on the very tick that casts it, and a snapshot taken afterwards silently "passes" a spell that did nothing. Re-run it after touching any `HD_*` constant. Balance bugs caught by exactly these checks and invisible from playing: out-of-combat regen at 3%/s handed back more HP per rest than a pull dealt; a shallow per-pull damage slope let the bot cruise every normal pull and die *only* on bosses, so every score in the field was 4, 9 or 14 and the leaderboard was three buckets. ⚠️ The harness itself hardcoded pack-HP/boss multipliers and printed stale fight lengths through two tuning passes — it now reads them out of the sim via `hdStartPull`/`hdPartyDps`. ⚠️ Its skill-ratio bar is **2.5×, not 4×**: both ends of that ratio move together when the encounter gets harder, so demanding 4× at an 8-pull target is chasing a number the design cannot reach.

**The game is a FIT-TO-VIEWPORT TAKEOVER and never scrolls, at any window size.** `.hd-fit` is `position: fixed; inset: 0` and covers the app header and nav; inside it `.hd-console` has a FIXED virtual size — `HD_VIEW_LAND` 1600×900 or `HD_VIEW_PORT` 440×900 — that `hdLayout()` scales to the viewport with a single transform (the trick `agpScaleDom` already uses for the picker previews). Fluid units cannot make that guarantee: five raid frames, a spell rail and a battlefield have real minimum heights, so past some viewport they must scroll, clip, or scale, and only scaling keeps every readout on screen. Because the console size is fixed, every inner measurement is a plain pixel value that always adds up. It activates on `selectAllGame('healer_dungeon')` and tears down in `returnAgPanelHome` (the one point every exit path runs through — `ag-back`, `leaveAllGamesTab`, switching games); `html.hd-view-open` locks page scrolling and ✕ / Esc leave. The takeover is also what makes „always fullscreen on mobile" work on **iOS Safari, which has no element Fullscreen API** — the fixed overlay is the mechanism, `agRequestFullscreen()` (called synchronously from the picker card's click, since `requestFullscreen` needs a live gesture) only additionally hides the URL bar. Three things this cost, all worth knowing: ⚠️ **measure the container, not the window** — `hdViewportSize()` reads `.hd-fit`'s own rect, after a pane reported a bogus `visualViewport` of 117×240 against a 1280-wide document; ⚠️ **`hdPickView` chooses the layout by rendered AREA, not by a width threshold** — a width rule sent a phone held sideways (812×375) to the portrait console and painted a 183 px strip on an 812 px screen; ⚠️ the canvas is `object-fit: contain` and `hdInitCanvas()` derives its backing store from the **letterboxed** size and the on-screen rect, not from `devicePixelRatio` alone, or the battlefield goes soft on any screen bigger than the console's virtual size. A handheld in landscape still scales text to ~5 px, so `.hd-rotate` (deliberately outside the scaled console) says so.

**Layout reads left-to-right the way an MMO does** (2026-07-28): your **character pane** (portrait, mana, the three stats as a character sheet), your **cast bar directly under it**, and your **spellbook** under that — then the party's raid frames, then the world. The spellbook icons carry a **WoW global-cooldown sweep** (`.hd-spell-sweep`, a `conic-gradient` whose `--sweep` angle unwinds from the remaining fraction), which exists because the GCD was previously invisible: casting on one hero and immediately clicking the next silently did nothing, and there was no way to tell why. The sweep shows whichever of the GCD, the in-flight cast, or that spell's own cooldown has longest to run; only waits longer than a GCD also print a number, since digits ticking over a 1.1 s window are noise. **The spellbook is BUILT from the picked class's spell table** (`healerBuildSpells`, rebuilt whenever `st.cls` changes) rather than being static markup — the buttons *are* the class. Raid frames are **Grid/VuhDo-style**: the CELL is the health bar (class-coloured fill over a grey track) with everything on ONE row — name, HP **as a percent**, the prediction number, buff pips, the target key — plus the incoming-heal, incoming-damage and absorb blocks painted on it and the healer's mana as a hairline along the bottom edge. They are a **fixed 34 px** (30 px portrait) and (rev 2) an **absolutely-positioned overlay pinned to the top-left of the board**, exactly where WoW's default raid frames live, which gives the battlefield the whole width back. The healer's own **mana bar sits directly under the five health bars** with the 5-second-rule pip beside it (rev 3): it was a 4 px hairline along the bottom of the healer's frame with the real number only on the character pane in the left rail, but in a fight your eyes never leave the frames and "can I afford this" gets asked as often as "who is lowest". On a phone that lets the whole character pane go — every one of its rows is covered elsewhere, and it only cost the scarce axis. **They are also DRAGGABLE** (rev 3, `hdSetupFramesDrag`): where your unit frames sit is a personal thing, so a ⠿ grip moves the whole block, the position persists per browser (`hd_frames_pos_v1`) and a double-click on the grip returns it to the corner. ⚠️ Two things this needs: pointer deltas are divided by the console's `--hd-scale` (one screen pixel is `1/scale` console pixels, so without it the block slides several times too fast on a small window), and the clamp-to-column is **skipped while the column still measures 0×0** — `healerBuildFrames` runs before layout, and clamping against an empty column pinned the frames to 0,0 and then wrote that back as the desired position, silently eating the home offset on every load. ### World Cup betting (Mundial)

The `⚽ Mundial` tab is **fixed-odds betting vs the house** on FIFA World Cup 2026 matches — unlike the peer-pooled CPMM markets, it mints/burns coins like slots/roulette. A player picks a match outcome (1 = home / X = draw / 2 = away); the real bookmaker decimal odds are **locked at bet time** and a winning bet pays `floor(stake × locked_odds)`. Losing stakes are burned. The displayed "szansa" per outcome is the **de-vigged implied probability** (`(1/odd_i) / Σ(1/odd_j)`).

Each user may place **at most one bet per match** (no top-ups, no opposite outcomes on the same fixture). The server enforces this inside the `placeBet` transaction; the frontend disables odds buttons once a bet exists for that match.

Events and odds come from **The Odds API v4** (`api.the-odds-api.com/v4`, sport key `soccer_fifa_world_cup`); **settlement results come from a second provider, football-data.org v4** (`api.football-data.org/v4`, competition code `WC`). Both are written **only** by the `football-action` Edge Function over its service `postgres` connection — the browser has SELECT-only access and **never sends odds** (the `bet` action reads the trusted odds already stored in `football_matches`). Match ids are The Odds API's hex event ids (text); football-data.org has its own numeric ids, so matches are looked up by team name instead (see below). The function is `verify_jwt = false` so it can serve the public `state` read and the cron path; the `bet` action validates the user JWT manually via `requireUser()`.

**Why two providers, and the 90-minute settlement rule:** the 1X2 market is standard betting convention — it settles on the **90-minute (regulation) result**, ignoring extra time and penalties, even for knockout matches. The Odds API's `/scores` only ever returns a match's actual final score with no way to tell whether it includes extra time, so a knockout match decided in ET would settle on the wrong side. football-data.org's fixtures expose `score.duration` (`REGULAR`/`EXTRA_TIME`/`PENALTY_SHOOTOUT`) plus a `score.regularTime` object whenever `duration` isn't `REGULAR`, which gives the true pre-ET score. `loadRegularTimeScores()` in `football-action` derives, per match: the **result score** (always regulation-time, drives `1`/`X`/`2`), the **display score** (real goals scored — `score.fullTime`, except for `PENALTY_SHOOTOUT` where `fullTime` bizarrely adds the shootout kicks on top of the goal count, e.g. a 1-1 draw decided 4-3 on pens is reported as `fullTime` 4-5, so `regularTime` is used for display too), and the stored `status` (`FT`/`AET`/`PEN`). This is explained to players in the "🥅" rule of the Mundial tab's "Jak działa Mundial?" panel. The Odds API and football-data.org spell a handful of teams differently (`DR Congo`/`Congo DR`, `Cape Verde`/`Cape Verde Islands`, `Czech Republic`/`Czechia`, `USA`/`United States`) — `canonicalTeam()`/`TEAM_ALIASES` in `football-action` normalize both sides before matching.

An **every-6h** `pg_cron` job (`football_hourly_sync`) `net.http_post`s the function with `{action:'cron'}` and the `x-cron-secret` header. The `cron` action: (1) **syncs events+odds** from The Odds API in one `/sports/{sport}/odds?regions=eu&markets=h2h&oddsFormat=decimal` call (the odds response carries fixtures, so no separate fixtures call) — picks a usable bookmaker per event, de-vigs the 1X2 prices, and upserts; (2) **settles** finished matches by pulling `/competitions/WC/matches?dateFrom=…&dateTo=…` from football-data.org (only spent when a match is still unsettled and past kickoff), deriving `1/X/2` from the regulation-time score and crediting winners' `potential_payout`; (3) **voids+refunds** stale matches (`voidStale`) — any match still `open` with no result **>12h past kickoff** (cancelled/abandoned/walkover/API gap/no team-name match) is marked `CANC`/`settled` and its open bets are refunded their stake and set to `void`. Void runs *after* settle so a genuine result always wins. An admin-only **`void`** action (`is_admin = true`, JWT-validated) does the same immediately for a specific `matchId` as a safety valve. **The Odds API free tier is 500 req/month, so the odds sync alone justifies the every-6h cadence (≤1 req/run ≈ 120/month) — football-data.org's free tier (10 req/min, no monthly cap) isn't the limiting factor.**

Config lives in Edge Function secrets: `ODDS_API_KEY` (the-odds-api.com key), `FOOTBALL_DATA_API_KEY` (football-data.org key), `FOOTBALL_CRON_SECRET` (shared with the cron block in `supabase/football.sql`), and optional `ODDS_SPORT_KEY` (default `soccer_fifa_world_cup`), `ODDS_REGIONS` (default `eu`), `ODDS_BOOKMAKER` (preferred bookmaker key, else first usable), `FOOTBALL_DATA_COMPETITION` (default `WC`). Frontend: `invokeFootball`/`loadFootball`/`renderFootball`/`buildMatchCard` plus a dedicated `#fb-overlay` bet modal, wired into `switchTab('football')` and the `football_matches`/`football_bets` realtime subscriptions. One-off manual corrections to already-settled matches (e.g. a match settled before the football-data.org switch landed) use `coin_transactions.reason = 'football_correction'`.

Net worth values held plant cards by rarity (common 20 / rare 50 / epic 150, NFT species excluded) and each NFT instance at `round(20000/edition_size * level)` — wired into both `user_assets_value`/`user_net_worth_breakdown` (`leaderboard-net-worth-items.sql`) and `economy_stats()` (`economy-stats.sql`).

**Phase 3 — P2P card/NFT/territory resale is now LIVE** via `supabase/farm-marketplace.sql` (run after `marketplace.sql` + `farm.sql`). It extends `marketplace_listings` with item linkage (`item_kind` `farm_nft`/`farm_card`/`farm_tile`, `nft_instance_id`, `card_species`, `farm_tile_x/y`), reusing the Targowisko bid/escrow/refund engine for coins. `create_farm_nft_listing` (reserves the instance via `farm_nft_instances.listed`), `create_farm_card_listing` (reserves **N free duplicates** — a bundle `qty`, default 1 — by decrementing `farm_collection.count`; see `farm-card-bulk-listing.sql`), and `create_farm_tile_listing` (reserves an owned empty non-migration tile via `farm_tiles.listed`) make listings; `buy_marketplace_listing`/`settle_marketplace_listing` are item-aware (call `farm_marketplace_deliver` → transfer NFT `owner_id`, credit a level-1 fungible card, or transfer `farm_tiles.owner_id` and set `asset_value` to the sale price), and `cancel_marketplace_listing` calls `farm_marketplace_release`. Listed tiles cannot be planted (`plant_crop` rejects `tile_listed`) and render a small `FOR SALE` sign on the farm board. `farm_nft_transfers` (public SELECT) logs every NFT `mint`+`sale` with price; `open_farm_lootbox` writes a `mint` row (guarded). The `marketplace_cards` view exposes the item columns. Frontend: the create-listing modal (`#ml-overlay`) has a "Co sprzedajesz?" toggle (`mlSellKind`) + item picker (`mlPopulateItemPicker`) → `createFarmListing`; `buildMarketplaceCard` shows a Farma item badge; clicking an NFT row in the Katalog opens `openFarmNftExplorer` (every serial slot + owners + price history).

### Ogródek / nav UI conventions (2026-07-25)

- **One crop card per `crop_type`, not per plant.** Every weekly NFT edition and every bred hybrid harvests into the shared `seasonal_bloom` crop backed by ONE `farm_market` row, so the 📈 Cennik tab groups defs through `farmCropGroups()` and labels shared crops from `FARM_SHARED_CROP_LABELS` („Kwiat sezonowy"), listing the contributing plants underneath. Rendering a card per plant printed the identical price/chart ~19 times and read as a bug. Differentiation between those plants lives in `base_yield`/`base_grow_minutes`, not in price.
- **Clicking an NFT row in 📖 Katalog opens `openFarmNftExplorer` — the single source of truth for that card.** It carries the stats block, the per-level ladder (`farmCardLevelTable(def, price, level, { nft: true })` — merge-worded costs), every serial slot, and the ownership/price history. The old „Pokaż wszystkie" button that opened a second modal is gone; fungible cards still open `openFarmLevelModal`.
- **Clicking an NFT in 🎒 Mój Majątek opens `openFarmNftModal` — the owned-instance sheet, the counterpart to the catalog's `openFarmNftExplorer` (which is about the *edition*).** Below the trading card it carries `farmNftIncomeBlock` (the headline **Zysk/doba as a RANGE**, plus a meter marking where today's NPC price sits inside the 30–100%-of-pułap band, the „dziś" figure, the weekly-contract premium, and the Renoma Kolekcjonera uplift) and `farmNftStatSheet` (yield/grow/harvests-per-week/crop, the live vs ceiling price, per-harvest and per-day earnings, serial, level, net-worth value, where the card physically is — planted on działka [x,y] / listed / in the collection — and what the next merge level would change plus its cost). **Every income figure is a range on purpose**: the anchor re-rolls to 30–100% of the catalog max twice daily, so a single number would always be wrong in one direction. The math is `farmPlantIncomeCalc(def, level, over)` — the same helper the plant picker uses — with `over` supplying the instance's effective stats via `farmNftIncomeCalc`/`farmNftStatsAtLevel`, because a **bred hybrid carries its own `stat_yield`/`stat_grow_minutes`** and deriving from the species def would misprice it. Do not route this through `farmNftStats().perDay`: that one is the byte-for-byte mirror of `farm_hybrid_stats()` used by the breeding preview and must keep using `base_price` unmodified. The collector bonus is shown as a separate labelled line rather than folded into the headline, so the range stays comparable with the catalog and the plant picker.
- **🌟 Co zasadzić (`majPlantAdvisor`) sits right under 🧺 Plony in Mój Majątek** — the short answer to „which of my cards deserves the tile?". `farmPlantableRanking()` merges fungible cards and NFT egzemplarze into ONE ranking (a level-12 Kukurydza legitimately beats a level-1 NFT) and keeps only what is free to plant right now, mirroring the plant picker's eligibility rules: a fungible card at level 2+ is an unlimited seed, level 1 is capped by copies not already in the ground, and an NFT is one planting per unlisted, unplanted instance. Sorted by `calc.dayHigh` (the top of the 30–100% price band = „najwyższy możliwy zarobek"), ties broken on today's price then the shorter grow time. `MAJ_ADVISOR_TOP_N` is **6** on purpose — this is a nudge above the collection, not a second catalog; the header count is what's on screen and the footnote names the leftovers. **A row carrying an active weekly-contract premium must stay flagged** (`🏆 kontrakt +N/szt` + a gold tint): the premium lifts BOTH ends of the range — on the 2026-07-29 board it doubled Kukurydza's ceiling from a base of 16 — so an unmarked row reads as a permanently better card and stops being one the moment the week ends.
- `farmTaxStatusCard()` and `buildFarmSeasonalBody()` follow the same shape: status pill → one plain-language lead sentence → the numbers → detail in `<details>` or a numbered block. Neither hardcodes dates any more (the tax note used to quote a fixed 03.07.2026).
- **One frame per screen.** `.farm-hub-body` is the hub's only outline; everything inside it separates with spacing, a single hairline, or a flat tint — never its own border. That is why `.maj-crop-card`, `.deed-chip`, `.farm-tax-card`, `.farm-seasonal-goal`, `.farm-seasonal-prize`, `.farm-ach-card` and `.nftx-fact` are borderless. Font weights top out at 700, and a colour wash is reserved for states you can act on (unpaid tax debt), not for every notable state. Don't reintroduce boxes-inside-boxes.
- `plCount(n, one, few, many)` handles Polish 1 / 2-4 / 5+ plurals — use it for any counted noun.
- **Wood is scenery only** (`.notice-board`, `.plot-sign`, `.farm-divider`). Chrome that carries controls — `.farm-topbar`, hub modals, panels — uses the neutral `--r-*`/`--sh-*` tokens.
- `.nav-tabs` are pill targets with an `--acc-dim` active state, **sticky at every width** (2026-07-26). The offset can't be a constant — the mobile header wraps to two rows (87px vs the desktop 58px) — so `syncNavOffset()` measures the header and the nav with a `ResizeObserver` and publishes `--nav-top`/`--nav-h`; anything that sticks below the nav (`.shop-category-filters`, the mobile dropdown's `max-height`) is expressed in terms of them. The measurement is skipped while `#screen-app` is `display:none` (pre-login), so the CSS fallbacks hold until the observer fires on the 0 → visible transition. **Being positioned is also what keeps the dropdowns clickable**: `.nav-tabs` has a `backdrop-filter`, which creates a stacking context, so while it was static (the old mobile behaviour) its `z-index: 200` dropdowns were trapped inside it and painted *below* every `position: relative` card on the page — the Ogródek covered the „Gry" menu. The chrome stack is now page popovers (`.gp-details-popover`, `.ftbl-menu`) 30 < `.nav-tabs` 40 < `header` 41 < modals/toasts 100+. The mobile bar wraps rather than scrolling horizontally — the dropdowns are absolutely positioned children and an `overflow-x` container would clip them — with content-sized centered pills (flex-grow made „Ogródek" balloon to half the bar), and under 761px `.nav-group` goes `position: static` so each menu is one full-width scrollable sheet under the bar instead of a narrow popup hanging off whichever wrapped pill was tapped.
