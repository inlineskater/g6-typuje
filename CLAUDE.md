# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Rynek Proroctw G6** — a company prediction market web app with virtual coins, a shared Texas Hold'em table, and small office games. Polish UI. Single static file (`index.html`) backed by a hosted Supabase project and Supabase Edge Functions for server-owned game actions.

Live URL: `https://inlineskater.github.io/rynek-proroctw-g6/`

## Deployment

There is no build step. Push to `main` → GitHub Actions copies `index.html`, `login_hero.jpg`, `games/` and `tabs/` to GitHub Pages, stamps the commit SHA into `BUILD_ID`, and writes `version.json`. The one gate is the **payload budget check**, which fails the deploy if `index.html` is over 1600 KB (see Architecture). That's the entire pipeline.

To apply database changes: paste the relevant SQL into the Supabase SQL Editor (Dashboard → SQL Editor → Run). There is no migration runner.

Deep-dive design docs that don't need to load on every task live in `docs/` — read the relevant one before making non-trivial changes to that feature: `docs/db-migrations.md` (full per-file migration rationale for every `supabase/*.sql`), `docs/seasonal-games.md` (per-game tuning history), `docs/healer-dungeon.md` (full sim/balance design), `docs/filler.md` (1v1 flood-fill: schema, matchmaking races, anti-farming), `docs/all-games-picker.md` (arcade storefront preview engine), `docs/farma.md` (farm gameplay/economy — grid, lootboxes, NFTs, pricing, land tax, marketplace), `docs/farm-ui-conventions.md` (farm frontend/UX conventions), `docs/bank.md` (Bank G6 investment products — rate/price derivations and the caps that keep them safe), `docs/BACKUPS.md` (data backup setup).

- `supabase/bank.sql` — **„Bank G6"** investment products on their own nav tab (`#tab-bank`, UI in `tabs/bank.js`): **🏦 Lokata** (hard-term deposit, 7d/+5% · 14d/+12% · 30d/+30%, **dynamic** cap, breaking early returns principal and forfeits interest), **🐷 Skarbonka** (no term, 0,60%/day simple, **dynamic** cap, interest locked for 7 days), **📜 Obligacje** (weekly series of **dynamic** size; 1 000 face, 8/day coupon, 20 days, **tradeable**, allowance `ceil(edition/active players)` per player, lifted in the issue's last 2 days), **🎰 Udział w Kasynie** (30 shares × 4 000, each paying **3% of the trailing-7-day positive casino house net** — the one product that mints nothing, only redistributing coins already burned, and pays 0 in a week nobody gambles), and **💍 „Sygnet Bankiera"** (`banker_signet`, 15 000 🪙 in the Sklep — the legendary ring's deal exactly: **2%/day of the whole cash balance, uncapped**). **LIMITS ARE DYNAMIC**: `bank_ensure_limits()` recomputes every per-player cap once a Warsaw day and freezes it in `bank_limits` — budget = 0,30% of cash supply × a health multiplier `TARGET/(TARGET+inflation)`, split 55/10/35 across lokata/skarbonka/obligacje and divided by active players, then clamped. So the Bank throttles itself when the game is already minting fast (on 2026-08-23 the economy was net-minting **+9 685/day = +2,68%/day** from the farm and lottery, giving health 27% and a lokata cap of 4 500 instead of the 16 000 a healthy economy allows). Rates are NOT dynamic and every position stores its own terms, so a limit change is never retroactive. ⚠️ **The interest base for `daily_interest` items is cash PLUS open Bank deposit principal** — cash-only made the Bank a trap (locking the max lokata earned +630 while forgoing 2 700 of Sygnet interest, a net −2 070, so the rational play was to use nothing); counting deposits makes every product purely additive. Don't simplify it back to `p.coins`. ⚠️ Budget fixes `cap × rate`, not either alone, so doubling rates and halving caps costs the economy the same and reads far better — that is why 30-day lokata shows +30%. Adds `bank_deposits`/`bank_bond_series`/`bank_holdings`/`bank_dividends`/`bank_limits` (SELECT-only for clients) and `bank_state`/`bank_open_deposit`/`bank_close_deposit`/`bank_buy_bond`/`bank_buy_share`/`bank_list_holding`/`bank_unlist_holding`/`bank_buy_holding`. **Settlement is LAZY-ON-READ** (`bank_settle_due()` at the top of `bank_state`, crash/wheel pattern) with an hourly cron at **minute 35** as a backstop — idempotent and date-driven with a 14-day lookback, and bond redemption pays any coupon day the accrual missed, so a cron outage delays payouts instead of losing them. Also **rewrites `award_daily_interest()`**: it pays any def with `effect_type='daily_interest'` at that def's own `effect_value`, honours `hero_item_defs.interest_cap` (NULL = uncapped, which both interest items are today), and pays **only the best single item per user** so the ring and the Sygnet cannot stack to 4%/day. ⚠️ **The Sygnet is ~85% of the whole feature's coin creation** (~7 215/day if all 11 players hold one, compounding, vs ~1 250/day from all four products combined) — it is the only unbounded term, and `interest_cap` on that one row is the knob, not the other products' limits. ⚠️ Every `profiles` update inside `bank_settle_due()` must aggregate per user first — `UPDATE profiles p SET coins = p.coins + x.amount FROM cte x WHERE p.id = x.user_id` updates a row **once** when the CTE holds several rows for it, silently dropping the rest (it lost 24 of 48 coupon coins in this file's first smoke test while the dividend table still recorded all 48 as paid). ⚠️ The primary share sale needs `pg_advisory_xact_lock`, not a row lock on the buyer's own profile, or the 30-share float becomes 31; and the `redeemed_at IS NULL`/`closed_at IS NULL` guard must sit on the UPDATE, not only in the CTE that selected the rows, or a concurrent settle pays twice. "One open match per user" is enforced by a real partial-unique-index constraint (trigger-maintained), not just app logic. **Bot matches never write an `arcade_scores` row, win or lose** — only PvP results score — the only fix that closes a free/risk-free farming vector against the best-score-ever leaderboard, since `arcade.sql`'s RPCs (and their rate-limit) are deliberately bypassed. Minesweeper as a **90-second score chase** over a stream of boards on a five-rung ladder (6×6/5 mines → 9×9/16): clear one, the next deals instantly and harder; hit a mine and you lose the board, the streak and **5 s off the clock** — but not the run, which is the rule the whole design rests on (a marathon that ended on a forced 50/50 guess would be miserable). - `supabase/chat.sql` — „Czat G6" office chat: an ICQ-style rail present on **every tab** (public room + 1-on-1 whispers + heartbeat presence). Adds `chat_messages` (`recipient_id IS NULL` ⇒ public room, non-null ⇒ whisper) + `chat_presence` (`last_seen`/`online`), both public-SELECT/no-client-write and realtime-published. Uses the **direct SECURITY DEFINER RPC** pattern from `canvas.sql` (no Edge Function): `chat_send(p_recipient, p_body)` (trim + 1000-char cap + ≥1s rate-limit — the only anti-spam throttle, like `record_arcade_score`), `chat_heartbeat()` (marks caller online + sweeps stale sessions offline, the presence analog of roulette's `evictStaleSeats`; returns the online id list), `chat_set_offline()` (immediate offline flip on logout), `chat_mark_read(p_peer)`. **RLS is the whisper boundary** — a message is SELECT-able only if it's public or `auth.uid() IN (sender_id, recipient_id)`, enforced for realtime delivery too, so a whisper reaches only the two parties (and can be sent to an OFFLINE user — stored, shown when they return). The offline→online / online→offline flip on `chat_presence.online` is the realtime signal `index.html` turns into ICQ „wszedł/wyszedł z sieci" notices. A minute `pg_cron` job (`chat_presence_sweep`) closes the last-user-leaves gap the heartbeat can't. **Constants mirrored in `index.html`:** `CHAT_STALE` (90s) ↔ `CHAT_HEARTBEAT_MS` (25s, client ≤ ⅓ rule), `CHAT_MAX_LEN` (1000), the ≥1s send throttle. Idempotent; run once via `supabase db query --linked`. Frontend: `initChat`/`chatIngest`/`chatOnPresence`/`chatHeartbeatPing` + the `#chat-rail` markup, wired into `showApp`/`doLogout` and the shared `db-changes` realtime channel. ⚠️ Its `chat_heartbeat()`/`chat_set_offline()`/`chat_presence_sweep` are **superseded by `chat-presence-quiet.sql`** — re-run that after re-running this.
- `supabase/chat-presence-quiet.sql` — run after `chat.sql` (supersedes its `chat_heartbeat()`/`chat_set_offline()`/`chat_presence_sweep` cron; re-run after re-running that file); idempotent. Kills the presence heartbeat's realtime fanout (2026-08-07). `chat.sql` wrote `last_seen` on **every** 25s beat, and `chat_presence` is realtime-published with the client on `event:'*'` — so every beat was RLS-evaluated and broadcast to every connected client (**N users ⇒ N²/25 messages/sec**), all of it discarded on arrival since `chatOnPresence()` early-returns when `online` didn't change. Measured on prod: the realtime WAL query ran ~2×/s with nobody playing. The fix **splits the hot column out of the published table** — `last_seen` moves to `chat_presence_beats` (NOT published, no client grants, RLS-on-zero-policies), and `chat_presence` is written **only when `online` truly flips**, via a conditional `ON CONFLICT … DO UPDATE … WHERE chat_presence.online IS DISTINCT FROM true` (verified: 0 rows written while already online, 1 on a genuine flip/join). Steady-state WAL on the published table is now zero; realtime carries only real join/leave events. `chat_set_offline()` is likewise guarded so a double logout is a no-op. Sweeps use `COALESCE(beat.last_seen, presence.last_seen)` so pre-migration rows stay sweepable. **No frontend change** — the client still reads `chat_presence(user_id, online)`, subscribes to the same table, and `chat_heartbeat()` still returns the authoritative online list for `chatReconcileOnline()`. `chat_presence.last_seen` is deliberately kept as the fallback column.
- `supabase/lottery-draw.sql` — the Loteria's **actual draw + payout**, plus the „🎰 Maszyna losująca" ceremony UI (2026-07-31). Run after `lottery.sql` + `canvas-paint-log.sql` + `lottery-fixes.sql`; idempotent. Calls (doesn't redefine) `mundial_lottery_standings()`. Adds `lottery_draws`/`lottery_draw_secrets` + three admin-gated RPCs: `lottery_draw_commit` → `lottery_draw_run` → `lottery_draw_cancel`. **Fairness model is COMMIT–REVEAL:** commit seals a secret seed and publishes only its hash; the draw mixes in public entropy (an operator `public_seed` + a `force` slider) so the operator visibly influences the outcome without being able to aim it. ## Architecture

The app shell — HTML structure, all CSS, and the shared JavaScript — lives in `index.html`. No bundler, no framework, no TypeScript. **Feature code does not live there**: seasonal games are in `games/*.js` and whole tabs are in `tabs/*.js`, each fetched the first time it is needed.

**Payload budget (enforced).** `index.html` grew 241 KB → 1.88 MB between May and August 2026 with no single commit looking unreasonable, until a mid-range phone needed seconds of parsing before first paint. CI now fails the deploy if `index.html` exceeds **1600 KB** (`.github/workflows/pages.yml`). Adding a feature means adding a `tabs/*.js` module, not another 40 KB inline. If something genuinely belongs inline, raise the budget in the same commit so it is a reviewed decision.

**Lazy tab modules.** `TAB_MODULES` maps a tab to its `tabs/*.js`; `ensureTabModule(tab)` fetches it once (promise-cached) and `withTabModule(tab, fn)` runs the entry point once it is there. Currently split out: `stats.js` (Statystyki/Skarbiec/coin race), `lottery.js`, `plinko.js` (Plinko **and** Koło Żubra), `shop.js` (Sklep/Targowisko/Zlecenia), `poker.js`, `bank.js` (Bank G6). The scope rules are the same ones `games/*.js` follows:
- a module owns its top-level `const`/`let` — index.html must **not** also declare them (redeclaration across classic scripts is a hard error)
- its `function` declarations overwrite the no-op stubs index.html keeps for teardown calls `doLogout()`/`switchTab()` make unconditionally
- it reads shared globals from index.html, which always runs first
- anything called **synchronously** from outside the tab (the farm hub, `showApp()`, `setupRealtime()`) must be hoisted into index.html instead — see the „Shared with tabs outside Sklep" block. Anything called from a **click handler** can just be wrapped in `withTabModule()`.

`scripts/extract-tab.py` performs the move and enforces those rules: it refuses a region that redeclares a name, leaks a `const` outside, or has top-level side effects (`--allow-side-effects` opts in when they are only listener wiring).

**On-demand libraries.** `ensureLib(name)` loads `lightweight-charts` (charts, Rynki only) and Turnstile (only if `CAPTCHA_ON` is ever switched back on). Only `supabase-js` is required to boot — the inline script builds `sb` at top level, so it cannot be deferred; it is preloaded in `<head>` and executed at the end of `<body>`.

**Mobile chrome.** Below 900px the header, nav bar and chat rail drop `backdrop-filter` and go opaque (last rule in the stylesheet, so it beats the later `.chat-*` definitions). They are sticky and on screen on every tab, so the blur was being recomposited on every scroll frame. `isolation: isolate` preserves the stacking context the chrome z-order depends on (popovers 30 < nav 40 < header 41).

**Supabase client** is loaded from CDN. The anon key is intentionally public — Supabase RLS and function grants are the security boundary.

### Data flow

1. `loadMarkets()` fetches markets, trades, and profiles in parallel then calls `renderMarkets()`.
2. `renderMarkets()` fetches the current user's positions (`positions` view), then calls `buildMarketCard()` for each market.
3. Realtime subscriptions on `markets` and `trades` tables update state and call targeted update helpers (`updateCardProb`, `updateCardChart`) instead of full re-renders where possible.
4. **Those handlers only touch the DOM while the Rynki tab is showing** (2026-08-07). `renderMarkets()` costs a `positions` round-trip plus a rebuild of every card (each with its own lightweight-charts instance), and it used to run on **every trade by anyone, on every client, on every tab** — so a busy market made the farm/casino tabs janky for people not even looking at it. The in-memory state (`markets[]`, `tradesByMarket`) is still updated eagerly on every event so the grid is correct the instant it is shown; only the render is deferred, via a `marketsDirty` flag that `switchTab('markets')` flushes with `flushMarketsIfDirty()`. **Keep that invariant when adding handlers: update state unconditionally, gate rendering on `activeTab`.** A market *resolution* still calls `refreshMeCoins()` unconditionally — that one really does move everyone's balance.
5. Likewise `football_bets` only calls `refreshMeCoins()` when `payload.new.user_id === me.id`. That table is `SELECT`-able by everyone (`USING (true)`), so realtime hands every client every player's bets, and only your own row can move your own balance.

### Auth

Nick + 5-digit PIN. Implemented as Supabase email/password auth using the synthetic email `nick@typuje.local`. A Postgres trigger (`handle_new_user`) creates the `profiles` row on first signup. Economy writes go through RPCs or Edge Functions; the admin-only garden stage/streak controls use column-limited direct updates protected by RLS.

### CPMM pricing

`p(YES) = no_shares / (yes_shares + no_shares)`. Markets start at `yes_shares = no_shares = 500` (50%). Constant product `k = yes_shares × no_shares` is maintained by `place_bet`. Shares out for a NO bet of X coins:

```
dN = (N × X) / (Y + X)
sharesOut = X + dN
```

### Payout formula

Resolution distributes the total pot via the RPC `resolve_market`. The formula (mirrored in `estimatePayout()` for the live UI estimate):

```
payout = user_amount_bet + losing_side_pot × (user_shares / total_winning_shares)
```

Winners always get at least their bet back; the losing side's coins are split proportionally by share count. The estimate and the actual SQL resolution use identical math.

### DOM helper

`el(tag, attrs, ...children)` creates DOM nodes. **Children must be strings or Node objects — never arrays.** When you need to mix text and multiple element nodes outside of `el()`, use `node.append(str, node, str, ...)` instead.

### Filler

Filler (`supabase/filler.sql` + `supabase/functions/filler-action`) is a **1v1 territory flood-fill** game (the classic 1990 Gamos Ltd DOS game, „7 Colors" internationally) added 2026-08 as arcade-only via „Wszystkie Gry"; the seasonal promotion is deployed and armed but **scheduled for no week** — the 2026-08-10 slot it had been given was reassigned to „Kulki G6" on 2026-08-05, because as the only PvP game it needs two willing players online at the same time and that is a bad bet for an unsupervised week. Everything below is live the moment a Filler week is scheduled. Unlike every other seasonal/arcade game, it is **server-authoritative for every move** (Poker/Roulette/Wheel model, not the client-replayed-tick-simulation pattern) — a "vs bot" match is just a 2-seat match where seat 1 is `(user_id NULL, is_bot true)` (Poker's `bots.sql` trick), so bot-mode and the public-queue-with-bot-fallback PvP mode share one Edge Function and one pair of tables (`filler_matches`/`filler_match_players`), and there is **zero parity contract** to maintain since the client never runs an authoritative sim. **Bot matches never write an `arcade_scores` row, win or lose** — only PvP results score — the only fix that actually closes a free/risk-free/unlimited-attempts farming vector against a best-score-ever leaderboard. ⚠️ The playfield is a **DIAMOND LATTICE** (2026-08-04), i.e. a square grid rotated 45° and re-indexed so it stays rectangular: odd rows sit half a tile right, rows overlap by half a tile, and a rhombus shares a full edge only with the two tiles above and the two below (same-row left/right touch at a point and are NOT connected). This geometry is the **one thing the client and server must agree on** — `neighbors4()` in the Edge Function decides which tiles a fill flows through, `games/filler.js` decides which visibly touch — so shipping `index.html` (auto-deploys on push) without redeploying the Edge Function gives a board whose fills contradict what the player sees. Board is **21×27=567 tiles, 7 colors** (renders 21.5×14, a 1.54:1 landscape field, because h rows are only (h+1)/2 tall); bot practice matches use a **15×19=285** board, ~30% shorter, which is safe to differ because bot matches never score and every dimension-dependent value is derived from the match row. `width × height` must stay odd (majority always decisive, ties structurally impossible). Starting corners are assigned **at random per match** — the lattice's corners have unequal degree, so a fixed assignment measured 43-45% for seat 0. `scripts/filler-balance.mjs` is a bot-vs-bot balance harness (not a parity contract) used to re-derive `FILLER_MAX_MOVES`/`FILLER_MOVES_PAR`/seat fairness whenever the board changes; it takes optional dimensions (`node scripts/filler-balance.mjs 15 19`). `games/filler.js` renders the server's board via a realtime doorbell (filtered per match id) + a 2s poll, as absolutely-positioned clipped rhombi (a CSS grid can't express the half-offset rows), where a diamond-shaped group of four same-color same-owner tiles is drawn as one double-size gem — an exact retiling, purely cosmetic, and the only thing that stops a grown one-color territory reading as a wall of specks. Picking a color paints optimistically client-side before the round trip (`fillerPreviewPick`, explicitly non-authoritative — the server snapshot overwrites it), and `sweepGlobal` is skipped on the `pick_color`/`resign` hot paths. **Seasonal (whenever a Filler week is next scheduled — `supabase/filler-seasonal.sql`): the weekly ranking is a LEAGUE, not a best-single-run** — the only PvP game in the rotation, so "best match wins the week" would mean one lucky win ends your week and you never play a second opponent. `filler_league_week(week_start)` is the single definition (current-week view, all-time view and Monday payout all call it): per match `(win?100:35) + round(score/10)`, multiplied by a **repeat-opponent decay** (1st 100% → 2nd 70% → 3rd 45% → 4th 25% → 5th 15% → 6th+ 10%), plus **60 × distinct opponents**. Losses score on purpose (otherwise you duck the strong players); the decay + breadth bonus are also the anti-collusion device. `filler_scores.opponent_id` is a real indexed column because the ranking groups on it. In seasonal mode the queue waits `FILLER_QUEUE_SEASONAL_MS` (150s) instead of 18s before the bot fallback (a bot match scores nothing there), and `state` returns a `waiting[]` nick list the panel shows as a „ktoś czeka — Dołącz" nudge. The frontend does no ranking math; `SEASON_LIVE_VIEW_SOURCES` in `index.html` routes both Filler and Bug Jumper's pre-aggregated `_current_week` views into the seasonal podium. Full design (schema, the legal-color rule, matchmaking races, the self-healing sweep + cron backstop, the bot heuristic, the score formula) is in docs/filler.md — read it before touching any of this.

### „Kulki G6" (`bubble_breaker`) — full seasonal game since 2026-08

**Bubble Breaker**, the Windows Mobile puzzle that shipped on every Pocket PC (the Dell Axim X51 one). A 15×15 board of 5-colour balls; tap a group of touching same-colour balls to pop it, balls fall into the gap, empty columns slide left, and the round ends when no pair is left. Score is **n×(n−1) per group**, so it is deliberately superlinear — one group of 10 (90) beats five groups of 2 (10) — plus **+1000** for clearing the board. Lives in `games/bubble-breaker.js`; the panel is `#seasonal-game-bubble-breaker`; seasonal SQL is `supabase/bubble-breaker.sql` + `supabase/functions/bubble-breaker-action`.

**Promoted from arcade-only 2026-08-05, debuts via override on the week starting 2026-08-10.** The promotion was cheap precisely because the sim was written pure and deterministic from day one — the Edge Function is a transcription of the fenced PARITY BLOCK, not a rewrite. **One panel node serves both modes**: `loadSeasonalTab()` shows it in place during its season (server-issued seed + round row + `submit`), `selectAllGame()` moves the same node into `#ag-game-slot` for a free arcade run (local seed, no round row, `record_arcade_score`, capped at 12000 in `arcade.sql`). The existing `#ag-game-slot` CSS already hides the seasonal aside/prizes there, so no new CSS was needed.

Four things worth knowing before editing it:

- **No tick clock — the replay is just `(seed, [tapped indices])`.** The cheapest replay in the rotation. Every tap must be a legal pop or the whole submission is rejected, and a round is only scoreable once no pair remains (`st.over`); quitting early is allowed but not submittable, or the best play would be to stop the moment the score peaks.
- **⚠️ That also makes it the one game where an offline solver over the server-issued seed is cheap.** Wall-clock is the guard: `BB_MIN_MS_PER_MOVE` (150 ms) × pops must have elapsed, with `BB_TIME_GRACE_MS` (1500 ms) of slack. Never remove this without replacing it — the sim itself has no notion of time and would accept 60 optimal pops in one millisecond.
- **Input is one rule, two behaviours.** A tap on the *currently selected* group pops it; anything else only selects. A mouse selects by hovering, so desktop pops on a single click; a finger has no hover, so touch naturally falls back to the original's tap-to-select / tap-again-to-confirm. Don't "simplify" this into two code paths.
- **The sim is pure and deterministic on purpose** (`bbInitState`/`bbPopAt`: no DOM, no network, no `Date`, seeded LCG), and `games/previews.js` runs the *real* game for the picker card rather than a look-alike. Keep that property. The `ids` array is cosmetic (it lets the renderer animate a ball from where it was to where it landed) but is drawn from the same seeded stream so a replay stays identical.

**Parity:** the block between the `// ── PARITY BLOCK START` / `END` fences in `games/bubble-breaker.js` and `supabase/functions/bubble-breaker-action/index.ts` must stay byte-for-byte equivalent (rendering constants sit deliberately *below* the fence). `scripts/bb-parity.mjs` is unlike the other harnesses: it **extracts and evaluates both blocks from the source files** instead of carrying a third hand-transcription, then checks them both textually and by fuzzing tap policies. Hero `score_bonus` is `effect_value × 10` here (not ×1 like Tetris) because a good run scores 400-900. Full design in docs/seasonal-games.md.

### „Uzdrowiciel G6" (`healer_dungeon`) — full seasonal game since 2026-08

A WoW Classic-style **dungeon healer** sim: a five-man party (tank/you/3 dps) faces an endless dungeon where every pull is harder and every fifth pull is a boss; the run ends only when **you** die. Score is **points** (depth + healing efficiency + a flawless-pull bonus + tempo), not pulls cleared. Lives in `games/healer-dungeon.js`; seasonal SQL is `supabase/healer-dungeon.sql` + `supabase/functions/healer-dungeon-action` (a byte-for-byte transcription of the fenced PARITY BLOCK in the game file, verified by `scripts/hd-parity.mjs`).

Two things are unusual vs every other seasonal game: **(1)** the class (`HD_CLASSES`: druid/priest/paladin/shaman) is chosen client-side before the round starts and stored on the round row alongside the seed — safe because all four classes are balance-asserted to the same HP-per-mana. **(2)** a round has no natural "clean" end — it only stops on death or the `HD_MAX_TICKS` replay-cost safety cap, both valid submissions.

A fallen ally doesn't end the run, only the healer's own death does. The console is a fit-to-viewport takeover (`.hd-fit`) at a fixed virtual resolution that scales to any window size, and never scrolls.

`scripts/hd-balance.mjs` is the balance harness: it asserts the 5-second mana rule, cross-class HP-per-mana parity (≤3%), boss telegraph timing, and that a good run lands in the target 7-11 pull band, among many other sim invariants.

### World Cup betting (Mundial)

The `⚽ Mundial` tab is **fixed-odds betting vs the house** on FIFA World Cup 2026 matches — unlike the peer-pooled CPMM markets, it mints/burns coins like slots/roulette. A player picks 1/X/2; bookmaker decimal odds are **locked at bet time**, a win pays `floor(stake × locked_odds)`, losses are burned. Displayed "szansa" is the de-vigged implied probability. **One bet per match** per user, enforced server-side inside the `placeBet` transaction.

Two providers, on purpose: **The Odds API v4** supplies events/odds; **football-data.org v4** supplies settlement results. Both are written only by `football-action` (`verify_jwt=false`, JWT checked manually in `bet`) — the browser never sends odds. **Why two providers:** the 1X2 market settles on the **90-minute regulation result**, ignoring ET/penalties, but The Odds API's `/scores` can't distinguish a regulation result from an ET one. football-data.org's `score.duration`/`score.regularTime` fields give the true pre-ET score, so `loadRegularTimeScores()` derives the result score, display score, and status (`FT`/`AET`/`PEN`) from there. `canonicalTeam()`/`TEAM_ALIASES` normalize team-name spelling differences between the two providers (matches are looked up by team name, not id, since the providers use different id schemes).

An every-6h `pg_cron` job (`football_hourly_sync`) posts `{action:'cron'}` with an `x-cron-secret` header. It (1) syncs events+odds from The Odds API, (2) settles finished matches from football-data.org, (3) **voids+refunds** any match still `open` >12h past kickoff with no result (cancelled/API gap/etc — settle always runs first so a genuine result wins over a void). An admin-only `void` action does the same immediately for one match.

Config (Edge Function secrets): `ODDS_API_KEY`, `FOOTBALL_DATA_API_KEY`, `FOOTBALL_CRON_SECRET`, optional `ODDS_SPORT_KEY`/`ODDS_REGIONS`/`ODDS_BOOKMAKER`/`FOOTBALL_DATA_COMPETITION`. Frontend: `invokeFootball`/`loadFootball`/`renderFootball`/`buildMatchCard` + a `#fb-overlay` bet modal, wired into realtime on `football_matches`/`football_bets`. Manual corrections to already-settled matches use `coin_transactions.reason='football_correction'`.

### Collaborative canvas (Wspólne Płótno)

The `🎨 Wspólne Płótno` tab is a shared **r/place-style pixel board** — one common **192×108** (16:9) grid that the whole office paints together, rendered near-fullscreen with a thin instructions/toolbar bar on top. Unlike a game, there is no score, and (2026-07-14) **every pixel is free for everyone, unconditionally** — the earlier 1-free-pixel-per-2h / pay-1-coin-on-cooldown split is gone (`supabase/canvas-free-for-all.sql` supersedes that RPC; the `canvas_cooldowns` table is left in place, just unused). A fixed ~16-color palette keeps the canvas coherent. The nav tab carries a small „Nowość" pill (`.nav-new-badge`, shared with the Targowisko nav button).

Unlike Mundial/poker, the write path is a **direct `SECURITY DEFINER` RPC** (`place_pixel(p_x, p_y, p_color)`), not an Edge Function — it mirrors the garden `water_plant()` cooldown pattern (minus the cooldown, now). The browser has SELECT-only access to `canvas_pixels`/`canvas_cooldowns` and calls `sb.rpc('place_pixel', …)`; the RPC validates bounds + hex color, then upserts the pixel `ON CONFLICT (x,y) DO UPDATE` (last-write-wins, so simultaneous clicks resolve to one final color).

The **grid bounds (192×108) are duplicated** between `supabase/canvas.sql` (the RPC) and `index.html` (`CANVAS_W`/`CANVAS_H`) — keep them in sync. Frontend: `loadCanvas`/`drawCanvas`/`placePixelRpc`/`onCanvasTap` + `cvSetup` pan/zoom pointer handling (`cv*` helpers), wired into `switchTab('canvas')` and a `canvas_pixels` realtime subscription (`applyCanvasPixelChange`) that patches single cells without a full reload. `fetchAllCanvasPixels` paginates the initial SELECT in deterministic `(x,y)` order because Supabase caps one Data API response at 1,000 rows; changes arriving during that multi-request load are replayed onto the completed snapshot so fresh pixels are not lost.

### Office chat („Czat G6", ICQ-style rail)

An always-on, ICQ-styled chat docked to the **left edge**, present on **every tab** — the `#chat-rail` markup lives inside `#screen-app` but **outside every `#tab-*` div** (right after `</nav>`), so `switchTab()` never unmounts it and it's naturally hidden until login. Collapses to a small „🌼 Czat" launcher pill (with a total-unread badge) so it never blocks gameplay. Three surfaces: **Pokój** (one shared public room), **Kontakty** (the full roster minus the hidden admin account, online-first sorted, per-contact unread badges, 🌼 green/grey status flowers), and a **whisper thread** (private 1-on-1, sendable even when the peer is offline).

Backend is `supabase/chat.sql` (see the file list above) — the **direct SECURITY DEFINER RPC** pattern (like `canvas.sql`), not an Edge Function. Presence is a `last_seen` heartbeat exactly like roulette seats: `chatHeartbeatPing()` calls `chat_heartbeat()` every `CHAT_HEARTBEAT_MS` (25s) while the tab is visible (plus on `visibilitychange`); a user is online until `last_seen` is older than the server's `CHAT_STALE` (90s), and the `chat_presence.online` flip is what the frontend turns into ICQ „wszedł/wyszedł z sieci" toasts + a local (non-persisted) system line in the room, with an optional off-by-default WebAudio beep. **RLS is the whisper boundary** (public OR `auth.uid() IN (sender, recipient)`), enforced for realtime too. Delivery rides the shared `db-changes` channel: `chat_messages` INSERT → `chatIngest()` (de-dupes by id, bumps unread, toasts), `chat_presence` `*` → `chatOnPresence()` (diffs vs the local `chatOnline` set, so `last_seen`-only heartbeat ticks are ignored). Messages render via `el()` (text nodes — no innerHTML), so bodies are XSS-safe. Frontend state (`chatRoster`/`chatOnline`/`chatRoomMsgs`/`chatThreads`/`chatUnread`) is reset in `doLogout()` after a best-effort `chat_set_offline()`. Keep the mirrored constants (`CHAT_HEARTBEAT_MS`↔`CHAT_STALE` ⅓ rule, `CHAT_MAX_LEN`, ≥1s send throttle) in sync with `supabase/chat.sql`. The 25s beat itself writes only to the unpublished `chat_presence_beats` table (`chat-presence-quiet.sql`), so `chat_presence` — and therefore realtime — sees a write **only** on a genuine online/offline flip; don't "simplify" that conditional upsert back into an unconditional one.

### Farma (farm grid + card economy)

**Farma** is the top-level nav tab **🌱 Ogródek** (`#tab-farm`) — a shared **13×4** DOM-grid field of individually-owned tiles, replacing the old zen-garden tab (migrated plant tiles reuse the original `buildPot` code). Core loop: **buy a tile** (escalating BURN price) → **open a loot box** (100🪙, `open_farm_lootbox`, 3 distinct rarity-weighted cards) → **level cards** (consumes dupes+coins) → **plant** on an owned tile (server-timed growth, 24h floor) → **harvest** (mints crop units that rot 5 days later) → **sell to the NPC** at a fluctuating „stalk market" price (rolls twice daily, dips per sale, recovers ~12%/hr).

**Phase 2 (live):** serialized NFT cards (`farm_nft_instances`, unique serial + persona name per instance) drop from the normal loot box at low weight until their edition sells out; NFTs level by **merging** two same-species same-level instances (`level_up_nft`), never by spending coins alone.

**Phase 3 (live):** P2P resale of cards/NFTs/tiles via `farm-marketplace.sql`, reusing the Targowisko bid/escrow engine.

`FARM_W`(13)/`FARM_H`(4) must mirror `supabase/farm.sql`; every farm coin reason must stay in sync with `economy-stats.sql` and `leaderboard-net-worth-items.sql`. **Full gameplay/economy design (grid & tiles, land tax, lootbox odds, card/NFT leveling, „stalk market" pricing, weekly contracts, marketplace resale, balance-tuning knobs) is in docs/farma.md — read it before touching any farm RPC or pricing constant.**

### Ogródek / nav UI conventions

A few cross-cutting conventions worth knowing before touching farm UI: **one card per `crop_type`, not per plant** (shared crops like `seasonal_bloom` get one `farm_market` row and one 📈 Cennik card, listing contributing plants underneath — don't render a duplicate card per NFT edition), and **any code naming a crop pile from a `crop_type` must go through `farmCropIdentity()`** — never `fmDefs.find(d => d.crop_type === ct)`, which labels a pooled pile with an arbitrary contributing plant the player may not even own. In 📖 Katalog, **bred hybrids never show a species-wide level or generic profit ladder**: their yield/grow/value are stored per instance from the exact parents, so precise stats belong in 🎒 Mój Majątek (a planted hybrid may still show its real instance-based income). **🎒 Mój Majątek is a portfolio dashboard**: net farm value/action alerts first, crop sale + the Top-3 all-owned `Dzisiaj`/`Przy pułapie` profitability ranking second, then context-aware collapsible groups for plant cards, NFT instances, plots and special items. The ranking includes planted/listed NFTs and uses one shared full-cycle gross projection with server-order level/hybrid/land/NFT rounding, the 24h floor, whole-harvest `farmSellQuote` batch impact, Collector Reputation and eligible weekly-contract bonuses; it never substitutes remaining grow time or tax repayment. Breeding has only a compact `Skrzyżuj` CTA in the NFT group; its rules/destruction warning/synergy and the collapsed office hybrid feed live in the breeding modal. **A serialized NFT is drawn with `farmNftEmoji(n)`/`farmNftIconFor(species, serial, speciesEmoji)`, never `def.emoji`** (2026-08-07) — icons are per species, which breaks down for `wild_hybrid`, the nakład-500 catch-all where one 🌈 stood in for every wild hybrid ever bred; each serial now maps into the **append-only** `WILD_HYBRID_ICONS` by `(serial-1) % length`, client-side and deterministic (no server column). `farmListingEmoji()` (Targowisko, via `fmNft`) and `farmTileCropEmoji()` (planted tile, via `planted_instance_id`) exist because those surfaces hold no instance row; species-level surfaces keep 🌈. **`plCount(n, one, few, many)`** handles Polish 1/2-4/5+ plurals for any counted noun. **Wood is scenery only** (`.notice-board`, `.plot-sign`, `.farm-divider`) — chrome that carries controls uses the neutral `--r-*`/`--sh-*` tokens; hub-modal panels avoid boxes-inside-boxes. **`.nav-tabs` are sticky at every width** via `syncNavOffset()` (a `ResizeObserver` publishing `--nav-top`/`--nav-h`, since the mobile header wraps to two rows); the popover stacking order is `.gp-details-popover`/`.ftbl-menu` 30 < `.nav-tabs` 40 < `header` 41 < modals 100+. Full detail (portfolio/groups, NFT explorer/modal split, profitability projection, tax-card layout shape, mobile nav-dropdown behavior) is in docs/farm-ui-conventions.md.
