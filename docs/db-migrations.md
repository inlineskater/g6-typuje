# Database migration files — full reference

Every `supabase/*.sql` file and its matching Edge Function, in the order they were introduced. CLAUDE.md keeps a condensed one-line-per-file index; this doc has the full run-order rationale, parity contracts, and design history for each one. Apply changes by pasting the SQL into the Supabase SQL Editor (Dashboard → SQL Editor → Run) — there is no migration runner.

- `supabase/schema.sql` — core prediction-market schema, run once on a fresh project

- `supabase/store.sql` — reward shop tables/RPCs used by the Sklep tab

- `supabase/plinko.sql` / `supabase/functions/plinko-action` — „Plinko G6" solo casino game; the Edge Function owns each drop's randomness, path, payout, and coin accounting, while the frontend only animates the trusted server result

- `supabase/crash.sql` / `supabase/functions/crash-action` — „Rakieta" (Crash) **solo** casino game; each player flies their OWN rocket (`crash_rounds`, one `running` row per user), the hidden crash point/time lives in `crash_round_secrets`, and the Edge Function (`start`/`state`/`cash_out`) owns the RNG, the lazy bust-on-read resolve, and the payout. Results land in `crash_spins` (wired into `economy-stats`/`hazard-views`/`coin-inflow-stats`). No shared table, no realtime; the client animates a freeze-proof per-frame delta-time clock and polls `state` to catch the crash. Postaw runs a **client-side 3 s launch countdown** (`CRASH_COUNTDOWN_MS`, big 3-2-1 digits + canvas ignition/smoke via `drawCrashScene('countdown', …, ignition)`) before `start` is invoked — coins commit only at zero, and a frozen RAF (tab switched mid-countdown) aborts the launch instead of firing it unwatched; `start` then creates the round with `started_at = now() + LAUNCH_HOLD_MS` (1 s in the future), so the client receives the response while the multiplier is still pinned at x1.00 (`elapsedMs` is NEGATIVE during the hold; `crashTick` renders the START! liftoff frame until it crosses zero) — liftoff is synchronized on screen and the rocket never has an unseen head start. **Cash-out fairness contract (WYSIWYG):** the WYPŁAĆ button value is a CONTRACT — `cash_out` pays the claimed `atMultiplier` EVEN ABOVE the hidden crash point (phantom cents the blind display painted before the reveal reached it), bounded by (a) arrival ≤ `CASHOUT_GRACE_MS` (450 ms) after `crash_at` and (b) a cap of `multAt(server elapsed + CLIENT_AHEAD_TOL_MS)` (250 ms legit display lead, mirrored by the `crashShownMs` clamp in `index.html`); a bot claiming the cap every round still loses ≈2% (`(1-HOUSE_EDGE)·exp(CRASH_GROWTH·700) ≈ 0.981`), so `cashout_multiplier` may legitimately exceed `crash_point` in `crash_spins`. Busts are revealed IMMEDIATELY (`resolveDueRound` flips the round the instant `now() ≥ crash_at`) and the grace works even on a round a racing 250 ms state poll just flipped to `busted` — `cash_out` locks the latest running-or-recently-busted round and converts the recorded 0-win spin back into the win (supersedes both the strictly-below-crash-point rule and the earlier delayed-reveal fix). To keep honest clicks inside the grace window, `start` schedules a **bust nudge** via `EdgeRuntime.waitUntil`: the worker sleeps until `crash_at`+120 ms, then POSTs a service-role Realtime broadcast (topic `crash_<roundId>`, event `bust`, empty payload — no secrets) that the client (`crashSubscribeBustNudge`) answers with a `state` pull, landing the explosion in ~150 ms; the 250 ms poll remains the fallback when the worker is evicted (>~150 s flights are capped by `MAX_MULT` anyway). **Parity contract:** `CRASH_GROWTH = Math.log(2)/15000` (doubles every 15 s — slowed from 10 s in 2026-07 so a given latency gap costs less multiplier) must match between `index.html` and the Edge Function
- `supabase/wheel.sql` / `supabase/functions/wheel-action` — displayed to players as **„Koło Żubra G6"** 🦬 (a Żubrówka/bison-grass-vodka reskin of the wheel; every internal identifier stays `wheel` — `wheel_spins`/`wheel_rounds`/`wheel_round_bets`, `wheel-action`, `WHEEL_*` constants, the `'wheel'` game key in stats views/`ACT_GAME_LABELS` — only user-facing strings changed) — a SHARED-ROUNDS casino game: ONE communal wheel with a SINGLE ordered set of 20 segments, no risk tiers (a bet is just a stake): 1× ×10 (jackpot 🦬), 3× ×2, 2× ×1 (ZWROT — stake back), 2× ×0.5 (half stake back), 12× ×0. Sum = 19.0 → **RTP 95.0%**. A round opens `betting` the moment the first player bets; `wheel_rounds` (`id`, `status`, `spin_at`, `segment_index`, `resolved_at`) and `wheel_round_bets` (`round_id`, `user_id`, `nick_snapshot`, `total_bet`, `ready`, `multiplier`, `total_won`, `UNIQUE(round_id,user_id)` — one bet per player per round) are both public-SELECT/no-client-write, realtime-published tables, mirroring the roulette pattern; `wheel_rounds_single_betting_idx` (partial unique index on `status='betting'`) guarantees at most one open round at a time. **Coin timing follows the ROULETTE convention:** `bet` only validates the caller's balance (locks the profile row FOR UPDATE, does not deduct) — coins move for every bet at once when the round resolves. **Resolution is lazy-on-read, crash-style:** `resolveDueRound` (SELECT ... WHERE status='betting' AND spin_at<=now() FOR UPDATE SKIP LOCKED) runs at the top of `state`, `bet`, and `ready`, so the frontend's 1 s poll on `state` (while a round is `betting`, gated by tab-active+visible) is what actually fires a due spin — realtime (`wheel_rounds`/`wheel_round_bets` postgres_changes) only tells clients something changed and triggers the same reload, it never drives the resolve itself. The betting window is `WHEEL_BETTING_WINDOW_MS` = 15 s (duplicated between `index.html` and the Edge Function; the server's `round.spinAt` is always authoritative — the client computes a clock offset from `serverNow` on every response for a synchronized countdown/spin across tabs). After betting, the same button becomes a `ready` vote: the Edge Function marks that bet's `ready` flag under the round lock, and when no unready bets remain it pulls `spin_at` forward to `LEAST(spin_at, now() + WHEEL_READY_GRACE_MS)` with a 3 s sync grace; a solo bettor can therefore fast-start too. **Lock ORDER is round row, then profile row**, identical in `bet()` (find-or-create the open round FOR UPDATE, then lock the caller's profile), `ready()` (round only), and `resolveOneRound()` (the due round is already locked via `resolveDueRound`'s FOR UPDATE before any bettor's profile row is touched) — so the paths cannot deadlock. The Edge Function draws one `segment_index` (0-19) server-side via `crypto.getRandomValues` rejection sampling and pays every bet on the round `floor(total_bet × SEGMENTS[segment_index] × luck)`, mirroring each payout into `wheel_spins` (unchanged shape minus the removed `risk` column — still one row per resolved bet, hazard/economy views need no changes) — a bettor who spent their coins elsewhere before the draw is skipped (`multiplier=0, total_won=0`, no charge, no payout). **Parity contract:** the ordered 20-element multiplier array (`WHEEL_SEGMENTS` in `index.html`, `SEGMENTS` in the Edge Function) must stay byte-for-byte identical — it literally IS the wheel. Gets the „Amulet Bezwstydnego Fartu" ×1.01 casino-luck boost like the other house games (`hasCasinoLuck`, copied verbatim from `plinko-action`), applied once per round draw (same luck roll for every bettor); `state` also returns `casinoLuckUntil` (aggregate `MAX(expires_at)` via `casinoLuckStatus`). Every house-casino tab shows a communal amulet banner with its game-specific effect and exact expiry (or an inactive hint) linked to the shop; the shop card shows the exact projected end date if bought now, stacking the item's duration onto the active shared window. House game: coins move directly on `profiles.coins`, no `coin_transactions` ledger rows. Frontend (`#tab-wheel`): a live "Zakłady tej rundy" panel shows every bet as it's placed (nick/stake/ready, gaining a win/loss result after resolve), a communal "Ostatnie rundy" strip (last 10 resolved, sector + biggest winner), plus the existing personal "Twoje zakręcenia" history from `wheel_spins`; after the bet is accepted, the POSTAW button (`.rl-btn.is-gold`) becomes the ready control. The canvas (`drawWheelBoard`) renders a single big ring (all the visual budget the removed risk tiers freed up — oversized multiplier labels, a decorative dark bezel, a gold bezel ring) painted in a **Żubrówka palette** (0x deep bottle green, 0.5x dried-straw/hay, 1x pale meadow green "ZWROT", 2x vivid bison-grass chartreuse, 10x molten gold with a 🦬 in the label) + a ~40-dot warm-gold LED rim that idle-pulses and CHASES during a spin + a dark-green center hub with a single tapered blade-of-grass bezier (the classic bottle motif) and a 🦬 mark, all driven by one continuous `requestAnimationFrame` loop (`wheelFrame`/`wheelUpdateAnimState`) that walks `idle → countdown → blind → landing → result`: a BLIND constant-velocity spin (`WHEEL_BLIND_SPEED`, ~2.5 rev/s) starts the instant `spin_at` passes locally with no result yet, then blends into an ease-out-cubic landing (`WHEEL_LANDING_DURATION_MS` = 3.5 s, whole-turn math reused from the old solo spin) once `segment_index` arrives; a tab that loads mid-spin with the result already known skips straight to a full reveal-style landing. `plinkoReducedMotion()` skips the blind spin/LED chase and jumps to a 300 ms settle. The nav button and page title carry a small pulsing „NOWOŚĆ" pill (`.wheel-nowosc-badge`, same pulse recipe as `.seasonal-dot`). Stats wired into `hazard-views.sql` (`hazard_stats.wheel_pl`, `game_transactions` UNION — hazardista column header shown as „Żubr"), `coin-inflow-stats.sql`, and `economy-stats.sql` (`hazard_house_net`) — all unchanged, since they only read `wheel_spins`. Run order: `wheel.sql`, then re-run `hazard-views.sql` + `coin-inflow-stats.sql` + `economy-stats.sql`.

- `supabase/lottery-draw.sql` — the Loteria's **actual draw + payout**, and the „🎰 Maszyna losująca" on the Loteria tab (2026-07-31). Run after `lottery.sql` + `canvas-paint-log.sql` + `lottery-fixes.sql`; idempotent. It **calls** `mundial_lottery_standings()` rather than redefining it, so it never goes stale against those three. Adds `lottery_draws` (public SELECT, no client write, realtime-published) + `lottery_draw_secrets` (no grants) and three admin-gated RPCs: `lottery_draw_commit` → `lottery_draw_run` → `lottery_draw_cancel`. **The fairness model is COMMIT–REVEAL, not "trust the server":** commit generates a secret seed, stores it in the no-grant table and publishes only `sha256(seed)`; the draw then takes public entropy from the operator — a free-text `public_seed` the office can agree on out loud plus `force` (1-100, the „siła zakręcenia" of the on-screen machine) — mixes both into the hash, reveals the seed, and pays out. So the operator visibly moves the outcome without being able to aim it, because the seed they'd need was sealed first. Round k's roll is `sha256(seed|public_seed|force|k)` → first 48 bits mod the tickets still in the drum, walked against the stored `snapshot` (frozen at draw time, ordered `tickets DESC, id ASC`): weighted, **without replacement**, so more tickets = more chances and nobody takes two prizes. Tiers 30/20/14/10/8/6% mirror `LOTTERY_TIERS`; the 12% dividend goes to every ticket holder. Payout is `coin_transactions` mints (`lottery_prize`/`lottery_dividend`) in the same transaction — **added to `economy-stats.sql`'s `ledger_minted` reason list**, patched into the LIVE `economy_stats()` by a guarded `DO` block (that function is ~12 KB and deployed copies drift; the block RAISEs if the list was reworded). `coin-inflow-stats.sql` needs nothing — its "other" bucket is a NOT-IN catch-all. ⚠️ **There is deliberately NO dry-run/preview:** revealing the seed and then letting the operator re-roll with different entropy is the exact attack commit–reveal exists to stop, so one commit = one draw (`lottery_draws_single_open_idx` also allows only one sealed draw at a time). To rehearse, commit a throwaway and run it. ⚠️ **PARITY CONTRACT:** `lottery_roll()`, the snapshot ordering, and the tier percentages are mirrored in `index.html` (`lotRollFromHex`/`lotVerifyDraw`/`LOTTERY_TIERS`), which re-derives every roll with SubtleCrypto and prints ✓/⚠ on screen — verified identical against Postgres on all six rounds. Break one side and every real draw starts failing verification. What the operator CAN still choose is *when* to draw (the snapshot is taken then); that is unavoidable in any raffle and is stated in the UI. **Frontend** (`buildLotteryMachineSection`, between the ticket hero and „Podział puli"): a canvas drum with **one ball per ticket** (cap `LOT_BALL_CAP` 300, then a proportional largest-remainder sample with ≥1 ball per participant). The ceremony is, in order: **(1) load** — every ball pours in through a hopper above the drum (`LOT_LOAD_MS`, shuffled spawn order so the stream is mixed, `b.loaded` gating so an unloaded ball gets gravity only and NO shell constraint — the wall clamp would otherwise teleport it into the drum from above); **(2) spin** — the operator's **siła zakręcenia** slider is LIVE and drives the drum both before the spin and BETWEEN balls, but is locked during the blind spin, the drumroll and a flight (`lotMachPreviewForce` gates on `phase === 'idle' || awaiting`; `lotWireCeremony` flips `disabled` from `onAwait`/`onBusy`). One `lotForceSpin(force)` formula is shared by `lotMachSpin`, the preview and `lotMachAwait`, so the slider means the same speed everywhere. ⚠️ Mid-ceremony it is COSMETIC — the winners were drawn and stored at the first spin, so from then on it only changes how fast the drum churns, which is why it is locked during the blind spin (leaving it live there would imply it still steers a result the RPC has already been called with) and is spelled out in the admin hint; **(3) one click per ball** — `lotMachRelease` → a `LOT_SURGE_MS` drumroll (drum winds up, gold ring pulses) → the ball flies the chute into its socket → reveal + hold → the button re-arms for the next place. ⚠️ **Reveal order is LOWEST PLACE FIRST (6 → 1)** and is PRESENTATION ONLY — the server still draws round 1 = 1st place, so the biggest ticket holders keep the best shot at the top prize; reversing it in SQL would break the parity contract for nothing. The finale (place 1) gets a bigger name, a longer hold, a white flash, camera shake, a vignette and confetti. ⚠️ **`lotMachRelease` and `lotMachStartEject` must both clear `m.reveal`**: the reveal branch is the LAST one `lotDrawPanel` checks, so a `reveal` left over from the previous ball is what the panel prints for the whole ~1 s flight of the next one — the panel announced the PREVIOUS place mid-spin. The click→landing window is now one branch (`pending`, reading the queue during the drumroll and `m.flying.win` once the ball is out) that shows the place and prize but never the nick, and a frame-by-frame invariant check over a full six-ball run confirms the airborne ball is always the one announced. **Colour is per PERSON, not per hash** (`lotColorAt`/`lotHuesFor`, golden-angle hue × 3 tone tiers): a hash reliably hands two people near-identical colours, which makes the legend useless. `lotHuesFor` is pure over the ordered list, so the **legend above the drum** (`buildLotteryLegend` — dot + nick + tickets + place badge, own row highlighted), the drum balls, the chute sockets and the winners-list dots can never disagree. ⚠️ The drum is an **AIR-MIX** simulation (`LOT_PHYS` = upward jet from the floor + full gravity + jitter + slow swirl), *not* a vortex: a smooth tangential/radial field always settles into a steady annulus — crank it up and every ball pins to the glass (washing machine), pull them inward and you get a hollow donut. Tuned by measuring the spread over a jet × spread sweep, then **tuned DOWN again** (jet 420→300, spread 900→300, top spin 7.8→3.6) because speed is a *readability* constraint: the point is watching one ball leave the drum. ⚠️ The machine is **THEATRE and decides nothing** — `lotRunDraw` starts the blind spin FIRST and calls the RPC while it tumbles (the Rakieta countdown pattern), then `lotMachDeliver` feeds it the server's winners; `lotMachRaf` is module-level, never a field on the machine, so a stale frame can't re-arm against a replaced one. ⚠️ **One clock per frame**: `lotMachStep` stamps `m.now = ts` and `lotMachDraw` renders from it rather than calling `performance.now()` itself — they differ by under a millisecond in the live loop, but reading two clocks means the drawn frame isn't the one just simulated and the machine can't be stepped deterministically at all (balls whose `spawnAt` had passed in the sim stayed invisible). ⚠️ **Any canvas `arc` radius derived from a time delta must be clamped** — `arc` THROWS on a negative radius, which aborts the rest of the frame and blanks the chute and result panel; the socket-landing pulse hit this. The old synergy guaranteed +15% **units** and −5% grow time, but every hybrid species harvests `crop_type='seasonal_bloom'` (base_price **50**) while the premium parents harvest dedicated crops (`aeae_banana` 120, `crystal_lotus` 80, `golden_sunflower` 55, `diamond_rose` 40) — so a hybrid grew more units of a far cheaper crop and **earned less per day than the parents it burned** (real case: 5870🪙/d + 2000🪙/d → 2961🪙/d). Parent stats are the **EFFECTIVE, level-scaled** ones, so burning a levelled parent is priced in. Two floors (the old `ceil(max(parentYield) × 1.15)` unit promise, and the hybrid species' own `base_yield`) keep cheap pairs sane. Generalises to every pair including the „Dziki Mieszaniec" catch-all and hybrid × hybrid chains. **Hybrids also inherit `max(parentLevels)`** instead of minting at level 1, so breeding no longer collapses net worth (`round(20000/edition_size × level)`). Because level is re-applied downstream (`harvest_crop`: `round(stat_yield × (1+(lvl−1)×0.5))`, `plant_crop`: `max(1440, stat_grow_minutes × 0.92^(lvl−1))`), the **STORED** stats are backed out of the effective targets — `stat_yield = ceil(yieldEff / ymult)`, `stat_grow_minutes = floor(growEff / gmult)` — so the level is not counted twice; rounding is directional so the +15% promise can only be met or beaten. `farm_hybrid_stats` therefore returns BOTH the stored (`stat_yield`/`stat_grow_minutes`/`level`) and the effective/displayed (`yield`/`grow_minutes`/`per_day`/`value`) numbers, and `breed_nft` writes the stored ones. Level inheritance alone fixed the value regression for the 6 curated recipes but NOT for the `wild_hybrid` catch-all, whose deliberately huge `edition_size` of 500 valued it at `40 × level` — so **value gets the same per-instance treatment as yield and grow**: the new `farm_nft_instances.stat_value` column holds the net-worth value **PER LEVEL** (the instance-level replacement for `20000/edition_size`), set by breeding to the better parent's per-level value whenever the species formula would come in under it (`ceil`, so `round(stat_value × level)` can't dip below the floor). NULL — every non-bred card, and every hybrid whose own formula already wins — keeps the species formula, so nothing else in the economy shifts. **The three net-worth consumers (`user_assets_value`, `user_net_worth_breakdown`, `economy_stats`) all contain the identical expression `round(20000.0 / ni.edition_size * ni.level)`; this file patches the LIVE definitions in place via a guarded `DO` block** (`replace()` on `pg_get_functiondef`, skipped when `ni.stat_value` is already present, and it RAISES if the expression isn't found) rather than re-transcribing three functions — `economy_stats` alone is 12 KB and deployed copies drift. Any future reword of that expression breaks the patch loudly instead of silently. The guarantee is "never worth less than the better parent", NOT the sum of both — `level_up_nft` isn't sum-preserving above level 1 either. **`stat_yield`/`stat_grow_minutes` needed no schema change** — they already exist and `plant_crop`/`harvest_crop` already COALESCE onto them. `farm_hybrid_stats` gains a 3rd arg (`p_hybrid`, the species `breed_nft` actually resolved after the sold-out fallback); the 2-arg form is DROPped to avoid an ambiguous overload. **The JS mirror in `index.html` (`farmNftStats` → `yieldExact`/`perDayExact`, and `farmBreedPreview`) must stay byte-for-byte equivalent** — both sides use the same `ceil(x − 1e-9)` guard so an exact-integer quotient can't round apart.
